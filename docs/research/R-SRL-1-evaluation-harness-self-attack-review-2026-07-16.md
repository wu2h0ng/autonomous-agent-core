## Summary verdict: REVISE_BEFORE_INDEPENDENT_REVIEW

The harness design is coherent in principle and the skeleton implements the core loading/gateway abstractions. However, several issues must be closed before independent review and freeze; otherwise the experiment risks leakage, weak baseline equivalence, or unfalsifiable HCW/outcome scoring.

---

## P0 findings (must fix before independent review)

### P0-1. Event gateway does not enforce identical call/token budget across arms
The preregistration §4 states all arms share "calls/tokens/retries and wall-clock budget." The current `RsrlEventGateway` only tracks wall-clock indirectly via `arm_budget_seconds` and does not meter provider calls, tokens, or retries. Without this, a baseline arm could exhaust tokens that Arm 3 would have used, or vice versa, breaking the matched-design claim.

**Mitigation:** Add a `BudgetLedger` per arm/unit that counts LLM calls, input/output tokens, retries and tool invocations; hard-stop any arm that exceeds the frozen budget.

### P0-2. `read_repository` exposes raw bytes but not build/test output contract
The gateway returns repository file bytes but does not expose a standardized way to run tests/builds and receive structured output. Each arm will implement its own test runner, introducing arm-specific tooling bias.

**Mitigation:** Expose `run_tests(selector)` and `run_build()` as gateway methods that return a typed `TestResult` / `BuildResult`. All arms must use these methods; direct shell invocation of pytest is prohibited.

### P0-3. No enforcement that baseline arms do not use SRL-internal structures
The public-state contract says baseline arms receive only raw bytes. The current gateway blocks `expected_outcomes.yaml`, but it cannot prevent an arm implementation from importing `agent_os_contracts.srl_environment` and constructing its own `SrlRelevanceAssessment` internally.

**Mitigation:** Define arm capability envelopes explicitly in code: Arm 3 may import SRL contracts; Arms 1/2/4 run in a constrained Python environment or have an import-time guard. At minimum, the harness must assert that baseline arm outputs never contain SRL-internal record types.

### P0-4. Hidden scorer is unspecified
The design doc describes the scorer interface but provides no implementation, no criteria for each event type, and no negative-map for what counts as failure. Without this, the "verified outcome" numerator in §8 of the preregistration remains under-operationalized.

**Mitigation:** Provide a concrete `RsrlHiddenEvaluator` with per-event-type plugins, decision trees, and example pass/fail verdicts for u00.

**Status:** CLOSED — all 9 u00 event types now have deterministic fail-closed plugins: TEST_FIXED, DECOY, INTERFACE_ADAPTED, CONFLICT_RESOLVED, RESTART_EQUIVALENT, UNCERTAINTY_RESOLVED, BELIEF_UPDATED, COMMITMENT_MET and HELP_ESCALATED. Each plugin declares VERIFIED/NOT_MET/UNRESOLVED/INVALID semantics and required evidence refs; 93 harness tests pass; ruff/pyright clean.

### P0-5. DeterministicOutcomeEvaluator integration is hand-wavy
The design says draft verdicts must be recomputed by `DeterministicOutcomeEvaluator`, but the mapping from R-SRL-1 expected outcomes to `ExpectedOutcome`/`ObservedOutcome` contracts is not specified.

**Mitigation:** Define the exact `ExpectedOutcome` schema for each event type and the `ObservedOutcome` builder from gateway action/help logs.

**Status:** CLOSED — `RsrlOutcomeEvaluator` now derives `KNOWN_EVENT_TYPES` from `RsrlHiddenEvaluator.DEFAULT_PLUGINS`, dispatches recomputation through the plugin map, and falls back to INVALID for unknown types. The u00 `expected_outcomes.yaml` carries typed fields for every plugin; integration tests cover full-u00 VERIFIED scoring and draft/outcome contradiction. 93 harness tests pass; ruff/pyright clean.

## P1 findings (should fix before freeze)

### P1-1. u00 fixture is not a real repository lineage
The sample unit uses a single `repo/main.py`. A real unit needs a starting snapshot with history, branches, tests and dependencies so that events like "new failing test" and "interruption and restart" are meaningful.

**Mitigation:** Replace u00 with a real git repository fixture generated by a script, or document that u00 is intentionally toy-sized and only tests harness mechanics.

### P1-2. No `HelpRequest` burden ledger
The preregistration §8 requires HelpRequest precision ≥ 0.80 and mandatory-help recall 100%. The gateway records help requests but does not compute burden metrics per window.

**Mitigation:** Add `HelpBurdenLedger` that consumes `SrlHelpRequest`s and emits `HelpBurdenReceipt` against the frozen `HelpBudget`.

### P1-3. HCW recorder is unspecified
The design mentions screen/terminal recording and a category CLI but provides no file format, no rater CLI, no time-segment data model.

**Mitigation:** Add a minimal `HcwAnnotation` schema and a CLI prototype; at least one pair of raters should pilot it on u00 before freeze.

### P1-4. No operator instruction/script standardization
Operator expectancy bias is acknowledged in the preregistration §5, but the harness does not encode standardized prompts or prohibited coaching.

**Mitigation:** Add `operator_protocols/` with exact scripts for Arm 1 setup, Arm 2 driving and Arm 3 help responses.

### P1-5. Restart state equivalence comparator not implemented
The preregistration §8.1 defines four fields to check. The harness does not export or compare post-restart state.

**Mitigation:** Add `export_state()` and `compare_state()` methods to the gateway; implement the comparator for Arm 3.

### P1-6. Wall-clock budget enforcement is not real-time
`arm_budget_seconds` is stored but not enforced during the run.

**Mitigation:** Add a timer thread or per-call budget check that raises `BudgetExceeded` and marks the unit `INVALID`.

## P2 findings (nice to have)

### P2-1. Event payloads are only digests at freeze
The design says payload content is injected at runtime. This is fine for harness testing but reduces freeze integrity. Consider freezing payload blobs as separate files in the manifest.

### P2-2. No naturalistic validation stream
The preregistration review P2-1 noted the highly structured sequence reduces ecological validity. The harness design does not add a secondary robustness check.

### P2-3. No pilot exclusion logic
The preregistration §9.1 says pilot units are excluded from the 8/9 count. The harness does not distinguish pilot units from real units.

## Recommended order before freeze

1. Close P0-4 (hidden scorer) and P0-5 (DOE mapping) first; without these the result is uncomputable.
2. Close P0-1 (budget ledger) and P0-2 (test/build gateway) to preserve matched-arm validity.
3. Close P0-3 (baseline arm envelope) to prevent leakage.
4. Close P1-1 (real u00) and P1-3 (HCW recorder) for interpretability.
5. Re-review with an independent methodology reviewer.
