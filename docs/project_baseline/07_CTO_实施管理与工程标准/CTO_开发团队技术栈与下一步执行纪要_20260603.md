# CTO 开发团队技术栈与下一步执行纪要

> 日期：2026-06-03  
> 角色：Codex CTO  
> 参与角色：Frontend Workspace Agent、Backend Core Agent、Development Team / Eval / DevOps Agent  
> 结论类型：技术栈决策与下一步 PR 任务包

## 1. CTO 结论

项目继续采用“窄核心、契约优先、可信闭环优先”的技术栈策略。

第一阶段不扩展成完整平台，不引入外部 Agent 框架作为 Core runtime，不让前端或 API 抢跑业务能力。React/Next.js 可以进入正式前端路线，但只作为 `Frontend Workspace Agent` 的实现模式，不新增独立 React Agent。

## 2. 推荐技术栈

### 2.0 语言分层共识

今天形成的长期语言边界：

```text
Python:
  OS Core / Trusted Loop / Eval / SQL Safety / EvidenceChain

TypeScript:
  Workspace UI / Developer CLI / Agent Tooling / Typed API Client

Java:
  Enterprise connectors / JVM data ecosystem / heavy SQL planner / private deployment adapter
```

该共识已固化为 `docs/decisions/ADR-0010-language-stack-boundaries.md`。任何把 OS Core 改成 TypeScript 或 Java 的提议，都必须通过新 ADR 和 CTO 审批。

### 2.1 产品实现根目录

- `ai-native-business-data-agent-os/` 是唯一产品实现根目录。
- `ai-agent-engineering-workflow/` 只作为研发辅助编排，不进入产品运行时依赖。

### 2.2 后端与 OS Core

- Python 3.11+
- 自研 `packages/os_core`
- `packages/contracts` 作为合同层
- 当前内部 contract 继续使用 Python dataclass / StrEnum
- 对外 API 边界后续使用 FastAPI + Pydantic / OpenAPI
- stdlib `unittest` + 项目自研 eval harness
- OpenAI adapter 与 OpenTelemetry adapter 保持 optional extras

### 2.3 SQL Safety

- 当前 SQL Safety 继续作为 MVP 门禁。
- 下一阶段引入或评估 `sqlglot` 作为 SQL parser-first 安全强化方向。
- 必须保持 SELECT-only、schema allowlist、参数绑定、limit policy、危险语句阻断。

### 2.4 前端 Workspace

- React / Next.js + TypeScript
- Typed API client
- F0/F1 使用 contract-shaped mock，不接真实 API，不发明后端字段
- Biome + TypeScript checks + Playwright smoke
- 样式先用轻量 CSS Modules / project CSS tokens，不引入重型组件库

前端模块必须围绕：

- Intent Workspace
- EvidenceChain Viewer
- ActionProposal Panel
- Trace Drawer
- Feedback Bar

### 2.5 CI / DevOps / Agent Runner

- GitHub Actions 作为质量事实来源。
- 本地 Agent Runner 只执行白名单命令和写 `.agent_runs/{run_id}`。
- n8n 只做触发、通知、审批和报表，不执行任意 shell，不合并 PR，不部署生产。

本地和 CI 基线命令：

- `ruff check`
- `ruff format --check`
- `python -m unittest discover -s tests -p "test_*.py"`
- eval report
- 后续补 pyright、secret scan、dependency scan

### 2.6 Java 长期定位

Java 不作为 MVP 主栈，也不进入 OS Core。

Java 适合后续用于：

- 企业级 Connector / Provider。
- JDBC-heavy 数据源。
- SAP / Oracle / Hadoop / Hive / Flink / Kafka 等 JVM 生态适配。
- Calcite-style SQL planner 或复杂 SQL 优化。
- Java 标准企业环境的私有化部署 adapter。
- 后期高吞吐服务，前提是有明确性能或客户部署证据。

Java 组件必须位于 ProviderContract、OperationContract、API 或 connector 边界之后，不能绕过 Python Core 的 Trusted Loop、EvidenceChain、SQL Safety、Eval 和 Trace。

## 3. 明确不采用

第一阶段不采用：

- LangGraph / OpenAI Agents SDK / CrewAI / AutoGen 作为产品 Core runtime
- Celery / Redis / Kubernetes / Vault / LaunchDarkly / 完整 RLS/RBAC
- Connector Marketplace
- Domain Pack SDK
- 完整 Data Fabric / NoETL / Active Metadata Platform
- 生产级 OpenTelemetry Collector / Grafana / APM 强依赖
- 前端重型组件库先行
- 前端真实 API 抢跑 contract
- TypeScript 或 Java 重写 OS Core
- Java 直接进入 MVP Core runtime
- R4/R5 自动执行
- 将 content-commerce、FaSoLa、客户 SDK 写入 OS Core

## 4. 下一步 PR 任务包

### PR-01: CI Local Parity

Owner：DevOps Workflow Agent + Test Automation Agent  
目标：建立 `ai-native-business-data-agent-os` 与 `ai-agent-engineering-workflow` 的本地/CI 基线一致性。

DoD：

- GitHub Actions 或等价 CI 配置明确 lint / format / unit / eval 命令。
- CI 成为合并事实来源。
- 失败不得由本地结果覆盖。

### PR-02: API Contract Boundary

Owner：Contract Agent + Backend Core Agent  
目标：先定义 `RunTrustedLoopRequest / RunTrustedLoopResponse` 等 API 层合同，不急于完整 FastAPI。

DoD：

- 合同测试覆盖成功和错误响应。
- CLI/runtime factory 使用合同序列化。
- OS Core 不 import domain pack、provider、example、action connector。

### PR-03: Trusted Loop Failure Result

Owner：Backend Core Agent + Contract Agent  
目标：将 SQL block、unknown metric、missing provider 等失败从未结构化异常升级为结构化失败结果。

DoD：

- 失败结果包含 status、errors、trace id。
- 失败路径也产生必要 trace / telemetry。
- 测试证明真实失败逻辑被绕过时会失败。

### PR-04: Eval Threshold Report

Owner：Eval Agent  
目标：把 golden query eval 从“能跑”升级为可作为门禁的报告。

DoD：

- 输出通过率、失败明细、阈值和回归分类。
- 失败样本不得直接改成 golden truth。
- prompt / model / metric / SQL / evidence / action 变更必须跑相关 eval。

### PR-05: SQL Safety Parser Hardening

Owner：SQL Safety Agent + Security Governance Agent  
目标：补强 CTE、subquery、quoted identifiers、function calls、LIMIT 参数异常、schema bypass 等反例。

DoD：

- 保留现有 SQL Safety 测试。
- 新增 bypass 会失败的测试。
- 如引入 parser，必须经 CTO / Security review，并避免成为不必要的 Core 重依赖。

### PR-06: Observability Gate

Owner：Backend Core Agent + Eval Agent  
目标：把 TraceEvent / TelemetryEvent 的业务、质量、成本、系统四类指标固定为 Trusted Loop 完成门禁。

DoD：

- 成功和失败运行都有 trace id。
- 四类 telemetry 至少有 MVP 表达。
- 不泄漏 prompt、token、key、敏感 payload。

### PR-07: Frontend Workspace React F0

Owner：Frontend Workspace Agent + Contract Agent  
目标：在 `ai-native-business-data-agent-os/apps/workspace/` 建立 React / Next.js + TypeScript 的 contract-driven F0。

DoD：

- 静态渲染 Intent、Evidence、Action、Trace、Feedback 区域。
- 使用 contract-shaped mock，不接真实 API。
- 不 import OS Core。
- 不改 backend contract。
- Playwright smoke 覆盖 EvidenceChain、SQL Safety、ActionProposal、空态、错态。

## 5. 执行顺序

推荐顺序：

```text
PR-01 CI Local Parity
  -> PR-02 API Contract Boundary
  -> PR-03 Trusted Loop Failure Result
  -> PR-04 Eval Threshold Report
  -> PR-05 SQL Safety Parser Hardening
  -> PR-06 Observability Gate
  -> PR-07 Frontend Workspace React F0
```

前端可以准备架构和脚手架，但真实 API 集成必须等 PR-02 和 PR-03 完成。

## 6. CTO 门禁

以下事项必须回到 CTO：

- breaking contract
- Core runtime dependency 变化
- SQL Safety 策略削弱
- EvidenceChain / Eval / Trace 被绕过
- auth、secret、permission、data egress、deployment 风险
- R4/R5 从 proposal-only 变成自动执行
- 为通过测试降低标准

## 7. 交付状态

当前决策：可以启动 PR-01 到 PR-03。  
PR-04 到 PR-06 作为同一里程碑内的质量门禁强化。  
PR-07 可以做 React F0，但只能使用 contract-shaped mock；真实 API integration 等待 API contract 和失败结果合同稳定。
