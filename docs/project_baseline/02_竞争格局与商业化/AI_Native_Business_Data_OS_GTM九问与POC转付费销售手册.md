# AI Native Business Data OS GTM九问与POC转付费销售手册

> 日期：2026-06-02  
> 用途：供创始人销售、BD、客户成功、售前和投资人沟通使用。  
> 适用阶段：0-1 参照客户、POC 设计、首批付费转化。  
> 核心判断：销售不卖“可信 AI”或“Agent OS 概念”，而卖一个可量化的业务响应闭环。

---

## 1. 九问总览

这九个问题是当前 GTM 的核心，不回答清楚，不进入正式销售和 POC：

```text
1. 目标客户是谁？
2. 最痛的业务问题是什么？
3. 客户现有系统是什么？
4. 不用我们，客户怎么解决？
5. 为什么现在必须解决？
6. 谁有预算？
7. 谁会反对？
8. POC 如何转付费？
9. 第一个闭环怎么验收？
```

这九问的作用不是写融资材料，而是帮助团队判断：

```text
这个客户是否值得追？
这个 POC 是否会付费？
这个业务场景是否值得做进 MVP？
```

## 2. 目标客户是谁

第一阶段目标客户：

```text
内容电商 / DTC 品牌
50-300 人
抖音或小红书有自营投放
日消耗 >= ¥5 万
数据团队 1-3 人
已有基础数仓或 BI，但 BI 基本沦为取数工具
增长负责人或数据 VP 对数字有直接压力
```

优先找：

| 条件 | 说明 |
|---|---|
| 有明确投放预算 | 没有投放预算，就缺少 ROI 异常场景 |
| 有数据团队但人手不足 | 完全没数据基础会变成数据建设项目 |
| 有 BI 但业务不用 | 说明问题不是没工具，而是工具没有进入行动 |
| 业务负责人直接焦虑 | 预算来自对 ROI 负责的人 |
| 最近发生过决策失误 | 最容易触发试点意愿 |

排除：

| 类型 | 原因 |
|---|---|
| 纯线下企业 | 数据闭环慢，首发验证困难 |
| 强监管金融、医疗、政务 | 合规和采购周期过重 |
| 无数据基础的初创企业 | 会拖入基础数据平台建设 |
| 只想买 ChatBI 的客户 | 容易陷入功能和价格比较 |
| 日投放消耗太低的客户 | ROI 异常损失不够大，付费理由弱 |

## 3. 最痛的业务问题是什么

客户真正的痛点不是“提数慢”。提数慢只是症状。

真正痛点是：

```text
周一早上 ROI 掉了 20%。
业务打电话给数据团队。
数据团队说“明天给结论”。
等结论出来，投放窗口已经过去。
报告写完，没人知道该执行什么、谁负责、怎么复盘。
```

这个痛点具备四个销售价值：

| 价值 | 说明 |
|---|---|
| 高频 | 每周都可能发生 |
| 高损失 | 每次可能是几万到几十万损失 |
| 高焦虑 | 业务负责人直接承压 |
| 高不确定 | 当前流程没有明确责任归属 |

销售表达：

```text
我们不是帮你更快拿一张报表。
我们帮你把 ROI 异常从“等报告”变成“当场拿到证据、原因和可讨论行动”。
```

## 4. 客户现有系统是什么

典型现状：

| 系统类型 | 常见选择 | 问题 |
|---|---|---|
| 云和数仓 | 阿里云 MaxCompute、腾讯云、MySQL、ClickHouse | 有数据，但业务不直接理解 |
| ETL / 调度 | DataWorks、自研脚本、定时任务 | 管道存在，语义不统一 |
| BI | Quick BI、帆软、Tableau、Power BI | 配了但利用率低，常变成取数工具 |
| 日常分析 | Excel、飞书表格、钉钉文档 | 口径散落，难以复盘 |
| 广告平台 | 千川、聚光、小红书后台 | 广告数据经常手动导出 |
| 协作审批 | 钉钉、飞书、企业微信 | 行动和数据证据脱节 |
| ERP / 订单 | 有赞、旺店通、聚水潭等 | 订单、库存、投放难以统一分析 |

核心问题：

```text
客户不是没有系统。
客户是系统之间没有共享语义层，也没有从洞察到行动的责任链。
```

销售表达：

```text
我们不要求你替换现有数仓、BI、广告后台或 ERP。
我们先接入它们，把散落在系统和 Excel 里的指标口径、证据和行动链路组织起来。
```

## 5. 不用我们，客户怎么解决

客户当前通常有三条路：

| 路径 | 当前做法 | 结果 |
|---|---|---|
| 人肉 SQL | 数据工程师临时写 SQL，业务等 2-3 天 | 响应慢，窗口错过 |
| 固定周报 | 每周固定模板报表 | 只能解释过去，不能进入行动 |
| BI 看板 | IT 或数据团队配几张看板 | 业务看完不知道该怎么执行 |

共同问题：

```text
洞察止步于 PPT / 看板 / Excel。
没有进入行动。
没有责任归属。
没有反馈复盘。
```

销售表达：

```text
传统方案回答“发生了什么”。
我们进一步回答“为什么、下一步做什么、谁来确认、执行后效果如何”。
```

## 6. 为什么现在必须解决

现在是切入窗口，因为三个压力同时出现：

### 6.1 流量红利结束

内容电商和 DTC 品牌已经不能靠粗放投放增长。ROI、素材疲劳、达人效果、库存周转都需要更快响应。

### 6.2 人力堆不动

一个高级数据分析师年薪通常可达数十万到百万级，并且经验容易随人流失。继续靠人肉分析扩张，成本和稳定性都不可控。

### 6.3 AI预算正在形成

老板已经开过 AI 战略会，预算开始出现。客户现在不是在问“要不要 AI”，而是在找“哪个 AI 项目能落地”。

最佳切入时机：

```text
客户刚因为数据响应慢导致一次可量化决策失误。
```

销售动作：

```text
不要泛泛问“你们有没有数据问题”。
要问“最近一次 ROI 异常、库存误判、GMV 下滑，花了多久才知道原因？损失多少？”
```

## 7. 谁有预算

预算人不是数据工程师，不是 IT，不是采购。

预算人是：

```text
对 ROI、GMV、转化、库存、现金流负责的人。
```

| 客户规模 | 预算决策人 | 预算范围 | 典型周期 |
|---|---|---:|---|
| 50-200 人 | CEO / 创始人直接批 | ¥10-50 万 / 年 | 1-2 个月 |
| 200-500 人 | 增长 VP / 数据 VP 提案，CEO 审 | ¥30-150 万 / 年 | 3-6 个月 |

销售判断：

```text
如果只和数据工程师、IT 或采购聊，永远容易停在 POC。
必须尽早确认业务 owner 和预算 owner。
```

预算验证问题：

1. 这个问题当前归谁负责？
2. 如果每周能少损失一次错误投放判断，预算从哪里出？
3. POC 成功后，谁能批准年费？
4. 采购需要哪些人同意？
5. 预算在本季度还是下一年度？

## 8. 谁会反对

### 8.1 数据团队

最危险的阻力来自数据工程师和分析师。

他们不是反对产品，而是担心被替代。

错误叙事：

```text
AI 帮业务自己问数，不再需要数据团队。
```

正确叙事：

```text
数据团队从写 SQL 的执行者，升级为 MetricContract Owner、EvidenceChain 审核人和 Eval Curator。
```

产品必须给数据团队专属能力：

| 功能 | 作用 |
|---|---|
| 指标管理台 | 让数据团队维护指标口径 |
| SQL 审核台 | 让数据团队审核高风险查询和模板 |
| Eval 仪表板 | 让数据团队定义系统正确性 |
| EvidenceChain 审核 | 让数据团队成为可信输出的治理者 |

### 8.2 IT / 安全

IT 安全的反对通常合理，不要绕开。

回应方式：

```text
Hybrid 部署。
数据不出客户内网。
模型调用经 Model Gateway 控制。
所有查询和行动都有审计日志。
```

### 8.3 财务

财务反对的是 ROI 不清。

回应方式：

```text
不是承诺“AI 很先进”，而是承诺 X 个高频业务问题从 2 天缩短到小时级或分钟级。
节省的人力时间、减少的错误决策、缩短的投放响应周期，都要量化。
```

注意：不要对所有问题承诺 30 秒。30 秒只适用于已接入数据、已定义口径和已沉淀模板的核心问题首答。

## 9. POC 如何转付费

POC 转付费的核心机制不是合同锁定，而是客户资产沉淀。

POC 期间必须沉淀：

```text
MetricContract
EvidenceChain 历史
ActionProposal 记录
Golden Query
业务复盘记录
客户专属口径和规则
```

这些资产一旦在系统中积累，迁移成本会自然超过采购摩擦。

关键判断：

```text
W6 是最佳签约窗口。
此时资产已足够多，客户已经看到价值；
但还没有进入“觉得 POC 够用了，先拖着”的惰性期。
```

POC 协议必须在开始前写清：

1. POC 周期：建议 6-8 周。
2. POC 成功标准。
3. POC 转付费条件。
4. 客户侧业务 owner、数据 owner、预算 owner。
5. POC 结束后的数据导出、保留和删除规则。
6. 若 W8 未转付费，按协议执行数据处置和访问关闭。

措辞原则：

```text
这是合规边界和数据安全承诺，不是逼单条款。
```

## 10. 第一个闭环怎么验收

最小验收单元只有一个场景：

```text
周一早上业务 VP 问：
“上周 ROI 为什么掉了？”

系统在核心已接入数据和已定义口径范围内，给出：
1. 与数据团队核对一致的数字；
2. 可点击查看的数据来源；
3. 口径和限制说明；
4. 至少一个可讨论的行动建议。
```

第一个闭环通过，不看“系统功能完整”，只看：

```text
业务用户是否主动回来用。
```

验收标准：

| 指标 | 标准 |
|---|---|
| 数字一致性 | 与数据团队核对一致 |
| 证据可追溯 | 数据来源、SQL、口径、时间窗口可查看 |
| 首答速度 | 已沉淀核心问题 P95 <= 30 秒；复杂归因允许进入异步分析 |
| 行动建议 | 至少 1 个 ActionProposal 可以被业务讨论或审批 |
| 自主使用 | 连续 2 周，业务用户不被引导主动提问 |
| 资产沉淀 | 至少 10 条 MetricContract、10 条 EvidenceChain 历史 |

如果仍需要销售或客户成功每次推动用户打开系统，不能算验收。

## 11. POC 转付费执行地图

```text
W0: 资格判断
  -> 确认 ICP、业务痛点、预算 owner、数据 owner、反对者
  -> 输出旅伴客户评分卡

W1: POC 协议和边界
  -> 签 POC 范围、成功标准、数据处置、转付费条件
  -> 确认单一业务闭环，不接受范围扩散

W2: 数据与口径接入
  -> 接入投放、订单、库存、内容或达人数据
  -> 产出首批 MetricContract 和 Golden Query

W3: EvidenceChain 首答
  -> 用真实问题生成可验证证据链
  -> 数据团队核对数字和口径

W4: ActionProposal 进入讨论
  -> 生成预算调整、素材替换、达人停投、库存预警等建议
  -> 明确风险等级和审批路径

W5: 真实业务使用
  -> 业务用户主动提出问题
  -> 至少 1 条 ActionProposal 被采纳、拒绝或进入审批

W6: 价值复盘与签约窗口
  -> 复盘响应时间、业务影响、人工节省、资产沉淀
  -> 提交年费方案和部署方案

W7: 采购推进
  -> 处理 IT、安全、财务和数据团队异议
  -> 确认合同、付款、上线计划

W8: 转付费或退出
  -> 付费：保留资产并进入正式客户成功计划
  -> 不付费：按协议导出、保留或删除数据，关闭访问
```

执行原则：

```text
W1 不签清楚边界，不进 POC。
W3 没有可信首答，暂停扩展功能。
W5 没有业务主动使用，说明价值没有到位。
W6 不谈付费，后面大概率进入永久试用。
W8 不转付费，必须退出或重新定义 POC。
```

## 12. 销售手册中的一句话

对客户：

```text
我们不替换你的数仓、BI、广告后台或 ERP。
我们把这些已有系统组织成一个可追溯、可行动、可复盘的业务决策闭环。
```

对业务负责人：

```text
当 ROI 掉了，你不应该等两天拿报告。
你应该在当场看到可信数字、原因证据和下一步行动建议。
```

对数据团队：

```text
你们不是被 AI 替代。
你们会从临时写 SQL，升级为指标口径、证据链和系统正确性的 owner。
```

对投资人：

```text
我们先用内容电商 ROI 异常这类高频高价值场景进入客户现场，
再把每次业务决策沉淀成 MetricContract、EvidenceChain、OperationTrace 和 KnowledgeAsset。
```
