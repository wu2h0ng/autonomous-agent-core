# SPINE Instrument Qualification Design

Status: `FOUNDER_APPROVED_FOR_IMPLEMENTATION_NOT_FROZEN_NOT_RUN`

## Goal and boundary

Prevent a SPINE successor from reaching freeze with stale experiment constants, stale request digests, or inconsistent provider authentication. This is Product-evaluation infrastructure, not Product runtime capability and not long-horizon evidence.

`SPINE-E2E-1` and `SPINE-E2E-2` source directories, preregistration files, locks, ledgers, receipts, and result records are historical evidence and remain byte-identical. The implementation adds common successor infrastructure and a new `SPINE-E2E-3` identity only.

## Selected architecture

### Derived identity, not copied constants

`SpineEvaluationIdentity.create(sequence, run_date)` accepts only the successor number and date. It derives `experiment_id`, `run_id`, module slug, provider model, API-key environment variable, dummy bearer, bank schema version, and qualification schema. Callers cannot independently supply these correlated values.

### Generated provider bank

The source template contains case payloads but no request digest and no provider model field. The deterministic builder injects the identity-derived model into request and response, computes each digest from the exact canonical request bytes, validates unique case IDs/digests, and writes canonical JSON. Checked-in generated output must byte-match a fresh rebuild.

### No-side-effect qualification

The qualifier:

1. rebuilds and byte-compares the complete bank;
2. validates expected case IDs and request/response model equality;
3. starts an identity-bound loopback replay server with a scratch ledger;
4. proves a wrong bearer is rejected and the identity-derived bearer is accepted;
5. proves the formal phase/provider ledgers remain absent;
6. emits a deterministic, hash-bound qualification receipt.

Scratch canary state is created outside the formal run root and is not a formal provider call, phase, or result.

### Formal-run consumption

`SPINE-E2E-3` uses the same identity object for provider environment configuration, replay-server bearer configuration, run/spec paths, schema names, and qualification receipt verification. The prepare command refuses before ledger genesis unless the committed receipt matches the exact identity, template, bank, and verifier bytes.

## Failure behavior

- Any old successor literal in the new template/generated bank/source scope: `INVALID_STALE_IDENTITY`.
- Request digest mismatch or generated-bank drift: `INVALID_PROVIDER_BANK`.
- Request/response/configured model mismatch: `INVALID_PROVIDER_IDENTITY`.
- Bearer rejection/acceptance mismatch: `INVALID_PROVIDER_AUTH`.
- Existing formal ledger during genesis check: `INVALID_EVALUATION_GENESIS`.
- Missing or stale qualification receipt: `INVALID_INSTRUMENT_QUALIFICATION`.

All failures occur before a formal phase ledger or provider ledger is created.

## Testing contract

- Tests are written and observed failing before implementation.
- Mutation tests independently change model, digest, bearer, case ID, and generated bytes.
- Genesis unit tests always inject temporary ledger paths; no test reads a preserved formal run by default.
- A post-ledger regression creates historical-looking ledgers in a temporary root and proves unrelated unit tests remain isolated.
- An immutable-scope check compares the E2E-1/E2E-2 paths against base commit `7d62270536f51c2ec99c242f84583c3cb2c8acbd`.

## Success boundary

Passing this task proves only that the successor evaluation instrument is constructable and qualified before freeze. It does not prove `SPINE-E2E-3`, D2, `LH-RECOVERY-1`, long-horizon advantage, autonomy, continual learning, or self-evolution.
