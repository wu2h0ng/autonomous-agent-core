# 2026 AI 原生企业级软件工程落地规范（项目适配版）

> 版本：V1.0  
> 生效日期：2026-06-01  
> Owner：CTO  
> 适用范围：AI Native Business Data Agent OS 项目，以及后续由 `ai-native-business-data-agent-os/` 派生的产品、试点和交付工程  
> 定位：本文件是项目级工程操作系统。它吸收企业级软件开发规范，但以本项目的 Agent OS、EvidenceChain、Eval、SQL Safety、Action Governance、Frontend Workspace 为中心落地。

## 1. 使用原则

本规范不是通用流程海报，而是后续项目管理、Code Agent 编排、PR 审查、CI 门禁、发布评审和试点交付的统一基线。

执行优先级：

```text
项目定义与价值叙事
  -> 架构 ADR / Architecture Review
  -> 本工程落地规范
  -> 90 天执行方案
  -> 单个 PR / Agent 任务
```

核心原则：

1. AI 原生，但人类 owner 对结果负全责。
2. Contract-first，不允许先写自由实现再补 schema。
3. Evidence-first，正式答案必须可追溯。
4. Eval-first，Agent、Prompt、模型、SQL、UI 关键变更必须可回归。
5. Safety-by-code，权限、SQL 安全、风险分级不能只靠 prompt。
6. Cost-aware，Token、模型调用、云资源都要进入成本归因。
7. No pseudo implementation，所有新能力必须有真实入口、失败路径和测试。

## 2. 项目阶段模型

本项目不照搬 50-500 人企业全部流程，而是分层启用。

| 阶段 | 当前项目含义 | 必须启用 | 暂缓启用 |
|---|---|---|---|
| P0 立项与基线 | 当前阶段 | PRD、架构评审、ADR、repo scaffold、Agent 规则、CI、基础 Eval | 完整 SAFe、正式 PMO |
| P1 MVP Trusted Loop | 当前到 90 天 | Contract、SQL Safety、Query、EvidenceChain、ActionProposal、Eval、API、UI smoke | 复杂工作流引擎、Marketplace |
| P2 试点闭环 | 3-6 个月 | 试点 runbook、反馈闭环、DORA 指标、成本归因、基础安全审计 | 完整 AIOps、混沌工程全覆盖 |
| P3 企业化 | 6-12 个月 | 权限、审计、发布策略、制品管理、SRE 值守、FinOps | Air-gapped、完整私有化 |
| P4 平台化 | 12 个月+ | IDP、Domain Pack SDK、Connector SDK、AgentOps 平台 | 自动高风险业务执行 |

## 3. 标准开发流程

### 3.1 需求与价值规划

每个需求进入开发前必须有 Goal Card。

必填：

- 用户是谁。
- 业务问题是什么。
- 为什么现在做。
- 成功指标是什么。
- 涉及哪些 contract。
- 是否影响 SQL Safety / EvidenceChain / ActionProposal / UI。
- 是否需要 eval case。
- 是否有安全、权限、成本、合规风险。

MVP 阶段采用轻量 WSJF：

```text
WSJF = (业务价值 + 时间紧迫度 + 风险降低/机会使能) / 工作量
```

进入 Sprint 的需求必须满足：

- 价值明确。
- 验收标准可测试。
- 上下游 owner 明确。
- 不以“AI 能做”为理由进入范围。

### 3.2 架构与设计

以下变更必须有 Architecture Brief 或 ADR：

- Contract/schema 破坏性变更。
- OS Core 模块边界变化。
- 新 Provider / Action Connector。
- Agent Runtime、Model Gateway、Eval Harness 变化。
- 权限、安全、审计、部署策略变化。
- 前端从 static mock 进入 live API integration。

架构评审必须回答：

- 这是不是当前阶段必须做？
- 是否有更小可验证切片？
- 是否破坏 OS Core 独立性？
- 是否引入外部 runtime 依赖？
- 是否有失败路径和 rollback 方案？
- 是否能进入 eval 和 trace？

### 3.3 开发与集成

每个实现任务必须遵守：

```text
Context Pack
  -> Contract / Test / Eval
  -> Implementation
  -> Reality Gate
  -> Ruff / Tests
  -> Review
  -> Memory / Index update
```

禁止：

- 先大规模写实现，最后补测试。
- 新增无人调用的 production-looking 模块。
- 通过 mock-only 测试宣称能力完成。
- 在 OS Core 中写 domain pack 逻辑。
- 让 prompt 替代 contract、权限或 SQL Safety。

### 3.4 测试与质量保障

当前强制门禁：

```text
python -m ruff check --no-cache .
python -m ruff format --check --no-cache .
python -m unittest discover -s tests -p "test_*.py"
```

MVP 必须覆盖：

- contract tests
- SQL Safety negative tests
- Trusted Loop unit tests
- API/application entrypoint tests
- golden query eval
- UI smoke（进入 F3 后）

AI 原生测试补充：

- Prompt 变更必须跑固定 eval 集。
- 模型切换必须做输出格式和关键语义回归。
- Agent 输出必须校验 schema。
- 对抗样本必须覆盖 prompt injection、越权请求、敏感信息泄露。

### 3.5 发布与部署

MVP 阶段发布对象先是可演示、可试点、可回归版本。

发布前必须有：

- 版本号或 commit SHA。
- CI 结果。
- eval 结果。
- 已知风险。
- rollback 方案。
- 数据/权限影响说明。

生产级阶段再启用：

- Docker image
- SBOM
- security scan
- artifact promotion
- blue-green / canary / gray release
- pre-prod smoke

### 3.6 运维与监控

MVP 先做 app-level trace，不提前引入重型 AIOps。

当前必须记录：

- trace_id
- intent
- metric
- provider
- SQL Safety result
- EvidenceChain id
- ActionProposal id
- feedback outcome

试点阶段新增：

- API latency
- model latency
- token usage
- eval pass rate
- error rate
- failed query category
- feedback adoption

### 3.7 反馈与迭代

所有负反馈必须能进入回归集。

标准流程：

```text
User feedback
  -> classify failure
  -> reproduce
  -> root cause
  -> add regression case
  -> fix
  -> eval pass
  -> update memory/index
```

## 4. AI 原生架构规范

### 4.1 Model Gateway

模型调用必须通过 Model Gateway 或明确的 application adapter。

要求：

- 支持模型路由。
- 支持超时和重试策略。
- 支持 token/cost 记录。
- 支持降级。
- 不在业务代码硬编码模型名。
- 不把 API key 写入代码、日志或项目记忆。

### 4.2 Agent 编排

Agent 必须有：

- 输入 schema。
- 输出 schema。
- 超时时间。
- 失败回退策略。
- 工具权限边界。
- trace 记录。
- human-in-the-loop 条件。

高风险 Agent 决策必须人工确认：

- 资金。
- 权限。
- 数据删除。
- 生产发布。
- 合规判断。
- R4/R5 业务动作。

### 4.3 RAG / Knowledge

RAG 或项目记忆只能作为辅助上下文，不能替代 source-of-truth。

要求：

- 文档来源可追溯。
- 更新有 owner。
- 敏感信息不入向量库。
- 重要知识进入 ADR、code_index、AGENTS 或正式 docs。
- 失败案例进入 eval，而不是只进入聊天记忆。

### 4.4 Prompt / Skill 治理

Prompt 和 Skill 是工程资产。

必须管理：

- 版本。
- owner。
- 适用场景。
- 输入输出 schema。
- 模型要求。
- eval 集。
- 正例和反例。
- token 成本基线。

Prompt 禁止承载：

- 权限判断。
- SQL 安全。
- 审批策略。
- 数据脱敏。
- 合规结论。

### 4.5 Eval-as-Code

Eval 必须像代码一样版本化。

MVP 评估维度：

- intent 命中率。
- metric contract 命中率。
- SQL Safety 拦截率。
- EvidenceChain completeness。
- Action risk classification。
- trace completeness。
- token cost per run。

## 5. AI 安全与合规

### 5.1 AI 专项风险

| 风险 | 控制 |
|---|---|
| Prompt injection | 用户输入隔离、工具权限白名单、输出 schema 校验 |
| 越权查询 | tenant/workspace/user/role/provider scope 检查 |
| 幻觉答案 | EvidenceChain 必填、MetricContract 引用、confidence/limitations |
| 敏感信息泄露 | 数据分级、日志脱敏、secret 扫描 |
| 模型供应链风险 | 模型来源登记、版本记录、可替换 adapter |
| 数据投毒 | 知识库写入审核、来源追踪、回滚 |

### 5.2 安全门禁

必须阻断：

- SQL write/DDL。
- 非白名单 schema。
- 明文 secret。
- 未经审批的 R4/R5 action。
- 未记录 trace 的正式答案。
- 未通过 EvidenceChain 的业务建议。

## 6. 研发效能度量

采用 DORA + AI 扩展指标。

### 6.1 DORA 指标

| 指标 | MVP 基线 | 试点目标 |
|---|---:|---:|
| 部署频率 | 每周至少 1 次可演示版本 | 每周 2-3 次 |
| 变更前置时间 | <= 3 天 | <= 1 天 |
| 变更失败率 | 建立基线 | <= 10% |
| MTTR | 建立基线 | <= 4 小时 |

### 6.2 AI 扩展指标

| 指标 | 含义 |
|---|---|
| Agent 一次通过率 | 首次 PR 通过 review + CI 的比例 |
| 伪实现拦截数 | Reality Gate 拦截的空壳/未调用/自证测试 |
| Eval 回归通过率 | golden/eval suite pass rate |
| Token per accepted PR | 每个被接受 PR 的 token 成本 |
| Token per golden loop | 每次可信闭环的 token 成本 |
| AI review 有效发现数 | AI review 被人类确认的问题数 |
| 人工返工率 | Agent 输出后需人工重写的比例 |

## 7. Token 经济学与 FinOps

每个 AI 功能点必须估算成本：

```text
development tokens
eval tokens
production tokens
embedding/storage cost
cache hit rate
fallback model cost
```

默认策略：

- 高风险架构、安全、contract review 用高质量模型。
- 文档、摘要、低风险测试生成用低成本模型。
- 生产链路必须记录 project_id / feature_tag / trace_id。
- 高频相同问题优先缓存。
- 超预算时先降级非关键任务，不降级安全和 EvidenceChain。

## 8. 组织能力与责任模型

AI 生成的代码由人类 owner 负责。

决策分级：

| 等级 | AI 权限 | 示例 |
|---|---|---|
| L1 AI 自主 | 可自动执行 | 格式化、局部文档、低风险测试草稿 |
| L2 AI 建议 + 人工确认 | 需 review | 代码实现、bugfix、测试生成 |
| L3 人工主导 + AI 辅助 | 需 owner 审批 | 架构、schema、API、数据库、发布 |
| L4 人工独占 | AI 只可提供材料 | 法律合规、隐私数据访问、伦理、安全风险接受 |

角色能力要求：

- Product Manager Agent：PRD、验收、优先级、用户价值。
- Project Manager Agent：计划、依赖、风险、节奏、状态。
- Architecture Agent：架构方案、ADR、边界、风险。
- Backend/Core Agent：contract-driven implementation。
- Frontend Workspace Agent：contract-driven UI，不改后端 contract。
- Eval Agent：golden cases、failure cases、回归评估。
- Security Agent：SQL、权限、secret、risk policy。
- Cost ROI Agent：token、云资源、Agent ROI。

## 10. 当前项目立即执行项

从 2026-06-01 起立即执行：

1. 所有开发任务必须经过 Reality Gate。
2. 新增模块必须有真实 entry point 或标注 staged seam。
3. Contract 变更必须更新 tests/eval/code_index。
4. Trusted Loop 相关变更必须保留 trace/evidence。
5. API 和 UI 只能消费 public contracts。
6. Frontend F0 可以开始，但 live API integration 受 contract gate 控制。
7. 每个 Sprint 输出 eval 结果和 token 成本基线。
8. 任何安全/权限/高风险 action 变更必须 CTO 或 Security review。

## 11. 不立即执行项

以下能力不进入当前 MVP 阻塞路径：

- 完整 SAFe。
- 完整 AIOps。
- 混沌工程全覆盖。
- 完整私有化和 Air-gapped。
- 全量 SBOM/Harbor/制品晋升。
- OPA/Temporal/OpenLineage 等重型平台能力。
- 高风险业务动作自动执行。
- Marketplace。

这些能力只有在试点和企业化阶段由 ADR 明确批准后进入实现。

## 12. Definition of Done

功能完成必须同时满足：

1. 价值和验收标准明确。
2. 有真实 entry point。
3. 有 contract 或说明不改 contract。
4. 有失败路径。
5. 有 unit/eval/smoke 中至少一种有效测试。
6. 相关质量门禁通过。
7. 不破坏架构边界。
8. 需要时更新 code_index、AGENTS、ADR 或 runbook。
9. PR summary 报告验证结果和剩余风险。

不满足以上条件，不允许声明完成。
