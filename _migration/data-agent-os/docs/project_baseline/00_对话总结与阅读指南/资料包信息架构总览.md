# 资料包信息架构总览

> 日期：2026-06-01  
> 用途：作为 AI Native Business Data OS 资料包的一层稳定导航和决策入口。  
> 原则：不移动原始权威文档，用多视图索引把同一批资料按受众、主题、场景和核心问题重新组织。

---

## 1. 为什么需要这一层

本资料包已经不只是战略备忘录，而是项目早期的基础底座，覆盖：

- 产品北极星。
- 阶段性落地边界。
- MVP 技术选型。
- 技术 PRD。
- 竞争格局和投资人叙事。
- 安全、生态、权限、部署。
- 评测样本和黄金业务闭环。
- CTO 实施管理、工程 SOP、Code Agent 治理。
- ADR 和未来代码仓库脚手架。

如果只按目录阅读，会出现三个问题：

1. 不同角色不知道先读什么。
2. 同一个问题分散在多个文档里。
3. 后续 Code Agent 或团队成员容易误读优先级。

因此新增本层信息架构：

```text
00_对话总结与阅读指南/
  资料包信息架构总览.md
  CEO阅读入口.md
  项目定义与价值叙事基线.md
  按受众阅读路径.md
  按主题索引.md
  按场景索引.md
  按核心问题索引.md
  关键术语表.md
```

## 4. 当前整理策略

不把现有长文档拆碎搬家。新增 CEO 决策入口和精简 HTML 报告作为阅读层，原始目录继续作为 source of truth。

原因：

1. 现有文档已经形成版本化上下文。
2. 直接移动会破坏引用和文件清单。
3. 多个角色需要同一份 source of truth，而不是多份拷贝。
4. 后续 Code Agent 更适合读稳定路径和索引，而不是追踪频繁搬迁。

更好的做法是：

```text
保留原始目录作为权威文档层
新增 00 目录索引作为决策导航层
新增 docs/ceo 作为经营决策压缩层
需要落地时再在 repo_scaffold 中生成代码目录
```

## 5. 后续维护规则

1. 新增重大文档时，必须更新 `README.md`。
2. 新增或修改资料文件时，必须更新 `文件清单.md`。
3. 新增架构决策时，必须写入 `docs/decisions/`。
4. 新增实现模块时，必须更新 `code_index.md` 和 `repo_scaffold/README.md`。
5. 新增业务场景时，必须更新 `按场景索引.md`。
6. 新增核心问题或客户痛点时，必须更新 `按核心问题索引.md`。
7. 新增关键概念时，必须更新 `关键术语表.md`。
