# 项目定义与价值叙事基线

> 日期：2026-06-01  
> Owner：CTO  
> 用途：统一项目愿景、产品身份、价值主张、核心术语和工程边界，作为员工、Agent、CEO、投资人和客户理解项目的第一层语义基线。  

---

## 1. 一句话定义

AI Native Business Data Agent OS 是面向企业 AI Agent 时代的业务生产操作系统：它同时重构数据工程范式和业务生产范式，把企业业务意图编译为可信数据产品、证据链、受治理业务行动、反馈学习和知识资产。它不是“只做治理控制面”的薄管道，也不是中间件包装；它拥有自己的语义理解、数据产品编译、证据生产、行动治理、组织权限、反馈学习和知识资产沉淀能力。

它让业务人员用自然业务语言提出问题或目标，系统把它编译成可验证的数据产品和证据链，再生成可审批、可追踪、可复盘的业务行动，并把结果沉淀为组织知识资产。

---

## 2. 对外价值表达

面向客户时，优先使用这个表达：

```text
我们帮助企业把散落的数据、指标口径和业务流程，变成一套可信的经营行动系统：
问得清，答得准，证据查得到，行动有人批，结果能复盘。
```

更短表达：

```text
把业务问题转化为可信数据证据。
把可信洞察转化为可审批、可追溯、可复盘的业务行动。
```

不要优先说：

```text
替代 BI
替代数仓
通用 Agent 平台
全自动经营
企业操作系统
```

这些表达会让用户误解范围，员工误解工程边界，Agent 误解实现优先级。

## 3. 愿景、使命和北极星

| 层级 | 定义 |
|---|---|
| 愿景 | 成为企业 AI Agent 时代的业务生产操作系统，让企业数据、证据、行动、反馈和知识资产形成持续进化的业务生产系统。 |
| 使命 | 让企业业务人员不再依赖低效提数、口径扯皮和黑盒 AI，而是能基于可信证据发起可治理的业务行动。 |
| 北极星 | 每个业务意图都能进入可信数据生产、受治理业务行动和知识资产沉淀闭环；EvidenceChain 是信任基础，Business Operation Loop 才是产品灵魂。 |
| 第一阶段目标 | 跑通 Trusted Loop：BusinessIntent -> MetricContract -> SQL Safety -> EvidenceChain -> ActionProposal -> Approval lite -> Feedback/Trace。 |
| 长期目标 | 从 AI-ready Data Foundation 延伸到 Agent-ready Business Operation，再沉淀 Enterprise Knowledge Asset。 |

## 4. 产品身份边界

### 4.1 是什么

| 身份 | 含义 |
|---|---|
| Business Data & Agentic Operations OS | 连接业务意图、数据产品、证据链、行动治理、组织记忆和知识资产的完整业务生产系统。 |
| Business Data Control Plane | OS 中负责策略、权限、路由、审计和治理的控制面能力；它是组成部分，不是产品全部身份。 |
| Trusted Data Agent | 第一阶段形态，负责把业务问题变成可信答案和 EvidenceChain。 |
| Governed Business Agent | 后续形态，负责把可信证据变成行动提案、审批和执行追踪。 |
| AI-ready Data Foundation lite | MVP 必须具备的最小数据底座，包括 SemanticObject lite、MetricContract、ProviderContract lite、DataProduct candidate、metadata/lineage snapshot。 |

### 4.2 不是什么

| 误解 | 正确边界 |
|---|---|
| 不是 BI 聊天框 | 它必须产生 EvidenceChain、Eval、Trace 和 ActionProposal。 |
| 不是数仓或湖仓替代品 | 它通过 ProviderContract 连接和治理数据源，不在 MVP 里重造完整数据平台。 |
| 不是通用 Agent 框架 | Agent Runtime 是内部运行时能力，不是卖给开发者的通用 Agent 框架。 |
| 不是 RPA 自动化工具 | R4/R5 高风险动作 MVP 只生成提案，不自动执行。 |
| 不是 Aloudata 上层插件 | 它必须拥有自己的语义契约、数据产品候选、证据链和行动责任链。 |
| 不是 FaSoLa 项目 | FaSoLa 只作为 Customer-0、Reference Domain Pack 和 Connector 来源。 |

## 5. 用户价值主张

| 受众 | 他们现在的痛点 | 我们给的价值 | 可验证结果 |
|---|---|---|---|
| CEO / 经营负责人 | 看不到经营异常背后的可信原因，行动责任不清 | 从经营问题直接进入证据、建议动作和责任追踪 | 关键问题响应时间缩短，行动有 owner 和复盘 |
| 业务负责人 | 提数慢、口径不一、分析结论难落地 | 用业务语言提问，拿到带证据的答案和行动提案 | 不再只收到报告，而是收到可审批动作 |
| 数据团队 | 重复取数、解释口径、救火修 SQL | 指标口径、SQL 模板、EvidenceChain 和 Eval 可复用 | 重复问题沉淀为 Contract 和 golden case |
| IT / 安全 | AI 越权查数、数据出域、动作不可控 | SQL Safety、Policy、Model Gateway、Trace、Approval | 可审计、可限制、可回放 |
| 一线员工 | 不知道该看哪个系统、下一步做什么 | 系统给出证据、建议动作、风险和审批路径 | 任务明确，反馈结果能沉淀 |
| 投资人 | 担心只是 AgentBI 或报表生成器 | 数据底座 + 行动闭环 + 知识资产形成复利 | 不是一次性问答工具，而是业务生产系统 |

## 6. 核心链路定义

### 6.1 MVP Trusted Loop

```text
BusinessIntent
  -> SemanticObject lite
  -> MetricContract
  -> ProviderContract lite
  -> DataRequirement / DataProduct candidate
  -> SQLTemplate / QueryPlan
  -> SQL Safety
  -> QueryResult
  -> EvidenceChain
  -> Answer
  -> ActionProposal
  -> Approval lite
  -> Feedback / Trace
  -> Eval regression
```

### 6.2 长期业务生产闭环

```text
Business Goal
  -> BusinessIntent
  -> Semantic Contract Kernel
  -> DataProduct Compiler
  -> EvidenceChain
  -> Business Agent
  -> ActionProposal / OperationContract
  -> Approval / Policy / Execution
  -> OperationTrace
  -> FeedbackEvent
  -> KnowledgeAsset
  -> Eval and semantic improvement
```

## 7. 核心术语权威定义

| 术语 | 权威定义 | 为什么重要 | 工程落点 | 常见误解 |
|---|---|---|---|---|
| Business Data Control Plane | OS 中负责策略、权限、路由、审计和治理的控制面能力；它支撑业务生产闭环，但不是产品全部身份 | 决定产品具备企业级治理和责任边界 | `packages/os_core/`、contracts、policy、trace | 误解为产品本体或普通后台管理台 |
| AI-ready Data Foundation | 让数据可被 AI 理解、查询、解释和治理的底座 | 没有它，AI 问数会幻觉 | SemanticObject、MetricContract、ProviderContract | 误解为完整数仓重建 |
| Agent-ready Business Operation | 让业务动作可被 Agent 受控建议、审批、执行、追踪和复盘 | 让产品从洞察进入生产 | ActionProposal、OperationContract、OperationTrace | 误解为全自动经营 |
| BusinessIntent | 业务问题或目标的结构化表达 | 替代报表需求和模糊 prompt | contracts、intent_runtime | 误解为用户原始文本 |
| SemanticObject | 业务实体、事件、关系、规则和动作语义的机器可读对象 | 指标和行动都需要共同语义 | semantic_runtime | 误解为知识图谱大工程 |
| MetricContract | 指标口径、owner、质量、verified query、证据模板和反馈指标的契约 | 防止口径冲突和黑盒计算 | contracts、semantic_runtime | 误解为指标名称字典 |
| ProviderContract | 数据源能力、权限、成本、质量、血缘和访问方式的契约 | 防止 Agent 任意访问数据源 | providers、data_access_plane | 误解为数据库连接字符串 |
| DataRequirement | 从业务意图推导出的数据需求 | 连接业务语言和数据获取 | data_product_compiler | 误解为 SQL where 条件 |
| DataProduct candidate | MVP 中可复用、可回放、带质量和血缘的候选数据产物 | 防止系统只做一次性问答 | data_product_compiler、evidence_chain | 误解为完整数据产品平台 |
| DataProduct Compiler | 把 BusinessIntent 编译为 DataRequirement、ProviderPlan、QueryPlan 和 DataProduct 的核心能力 | 对标 Aloudata AIR/CAN 的长期核心 | data_product_compiler | 误解为 ETL 工具 |
| SQLTemplate | 可参数化、可审查、可回归的 SQL 模板 | 降低 NL2SQL 幻觉 | query_runtime、sql_safety | 误解为模型自由生成 SQL |
| SQL Safety | 只读、白名单、参数绑定、limit、危险语句拦截和审计 | 企业信任底线 | sql_safety | 误解为 prompt 里提醒模型不要写 |
| EvidenceChain | 答案背后的证据链，包含问题、意图、口径、SQL、数据源、质量、权限、结论和限制 | 信任基础设施；无证据不进入决策 | evidence_chain | 误解为产品全部灵魂、日志或解释文本 |
| ActionProposal | 基于 EvidenceChain 的业务行动提案 | 从分析走向业务动作 | action_proposal | 误解为自动执行 |
| Approval lite | MVP 轻量审批记录 | 给高风险行动建立人类责任入口 | approval_lite | 误解为完整 BPM |
| OperationContract | 业务动作的输入、权限、风险、幂等、回滚和审批契约 | 后续安全执行动作的前提 | action_governance、action_connectors | 误解为 API wrapper |
| OperationTrace | 业务动作从提案到审批、执行、反馈的端到端记录 | 审计、责任和复盘基础 | trace、operation_trace | 误解为普通运行日志 |
| FeedbackEvent | 行动后的业务结果、人工评价和指标变化 | 形成系统学习闭环 | feedback | 误解为用户点赞点踩 |
| KnowledgeAsset | 经过审核、版本化、权限控制和评测绑定的企业知识资产 | 长期护城河 | knowledge_memory | 误解为 RAG 文档片段 |
| Eval Harness | 对 intent、metric、SQL、evidence、action 的回归评测框架 | 降低模型幻觉和回归风险 | tests/eval、eval_hub | 误解为单元测试替代品 |
| Golden Business Loop | 从业务问题到证据、行动和反馈的标准样本 | 让产品价值可验收 | domain_packs、tests/eval | 误解为 demo 文案 |
| Domain Pack | 行业指标、问题、模板、动作和评测样本的可复用包 | 防止行业逻辑污染 Core | domain_packs | 误解为客户定制代码 |
| Model Gateway | 模型路由、BYO Key、预算、数据边界和调用审计入口 | 模型可替换且可治理 | model_gateway | 误解为简单 OpenAI client |
| Self-developed Agent Runtime | 自研 Agent 运行时、工具注册、上下文、结构化输出和 trace | 避免产品 Core 被外部框架锁死 | agent_runtime | 误解为 LangGraph/CrewAI 包一层 |

## 8. Aloudata 对标时的统一口径

Aloudata 代表的是 AI-ready data foundation 的核心战场：

```text
AIR: Data Fabric
BIG: Active Metadata
CAN: NoETL Metric Semantic Layer
Agent: NL2MQL2SQL Analytics Agent
```

我们的口径：

```text
Aloudata makes enterprise data AI-ready.
We make enterprise business agent-ready.
```

内部解释：

- Aloudata 能做的底座能力，我们必须逐步纳入自己的架构。
- MVP 不重造完整 Data Fabric / NoETL / Active Metadata。
- 第一阶段只实现 AI-ready data foundation lite。
- 我们的上位差异是 DataProduct Compiler、EvidenceChain、OperationTrace、Action Governance、FeedbackAsset、KnowledgeAsset 和 Agent-ready Business Operation。

## 10. Agent 理解规则

所有 Code Agent、Product Agent、Architecture Agent 和 Review Agent 必须遵守：

1. 如果术语冲突，以本文档和 `code_index.md` 为准。
2. 如果范围冲突，以 ADR 和 repo scaffold 为准。
3. 如果价值叙事冲突，以本文档第 2 节和第 5 节为准。
4. 如果实现优先级冲突，以 MVP P0/P1/P2 文档为准。
5. 不得把 “Agent OS” 理解为通用 Agent 框架。
6. 不得把 “Data OS” 理解为重建数仓、湖仓或完整 Data Fabric。
7. 不得把 “Action” 理解为高风险自动执行。
8. 不得把 “EvidenceChain” 简化为自然语言解释。
9. 不得把 “KnowledgeAsset” 简化为向量库文档。
10. 不得把 FaSoLa 写成产品身份。
11. 不得把 "AI Native Business Data Agent OS" 降格理解为只有治理控制面、中间件或薄管道。控制面、MCP Gateway、Model Gateway、Workflow Bridge 都只是组成部分；产品本体必须拥有语义理解、数据产品编译、证据生产、行动治理、组织权限、反馈学习和知识资产沉淀能力。每个模块必须有实质逻辑，不是只有契约和骨架。

## 11. 价值是否讲清的检查清单

任何新文档、PRD、售前材料、架构设计或 Agent 输出，必须能回答：

1. 这个能力服务哪个业务痛点？
2. 它增强的是可信数据、受治理行动、反馈学习，还是知识资产？
3. 用户为什么愿意为它付费？
4. 它是否能被 EvidenceChain、Trace 或 Eval 验证？
5. 它是否会让 MVP 变成重型平台工程？
6. 它是否会让产品退化为聊天 BI、报告生成器或 RPA？
7. 员工能否知道自己要交付什么对象？
8. Agent 能否知道代码应该放在哪个模块？
9. 客户能否用一句话理解这个功能的业务价值？
10. CEO 能否用它判断项目是否更接近北极星？
