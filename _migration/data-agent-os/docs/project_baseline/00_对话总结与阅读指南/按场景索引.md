# 按场景索引

> 日期：2026-06-01  
> 用途：按业务场景组织资料，帮助选择首发试点、定义闭环、准备评测样本和交付边界。

---

## 1. 场景选择原则

首发场景必须满足：

1. 高频。
2. 指标明确。
3. 数据相对可得。
4. 业务 owner 愿意参与。
5. 行动建议可验证。
6. 风险可控，第一版不需要高风险自动写操作。
7. 能沉淀 golden query 和 golden business loop。

不满足这些条件的场景，即使商业想象大，也不适合 MVP。

典型问题：

- 最近 7 天爆款内容有哪些？
- 哪些达人带来的 GMV 最高？
- 哪些标签转化率最高？
- 竞品最近在推什么类型的商品？

推荐资料：

1. `05_业务问题与评测样本/业务问题样本.md`
2. `05_业务问题与评测样本/黄金查询样本.md`
3. `05_业务问题与评测样本/黄金业务闭环样本.md`
4. `06_方案评估与落地边界/AI_Native_Business_Data_OS_阶段性落地方案.md`

MVP 闭环：

```text
业务问题
  -> 内容/达人/标签 MetricContract
  -> SQL Template
  -> EvidenceChain
  -> 内容选题或达人合作 ActionProposal
  -> 人工确认
  -> 结果反馈
```

注意：

- 内容电商只能是首发 Domain Pack，不应写进 OS Core。
- 浏览器采集和平台 API 都应作为 Provider，而不是核心身份。

## 3. 投放 ROI 诊断

典型问题：

- 今天 ROI 趋势如何？
- 哪个投放计划 ROI 最低？
- 聚光和千川 ROI/CAC 对比如何？
- 如果要恢复到目标 ROI，应该处理哪些计划？

推荐资料：

1. `05_业务问题与评测样本/黄金查询样本.md`
2. `05_业务问题与评测样本/黄金业务闭环样本.md`
3. `06_方案评估与落地边界/AI_Native_Business_Data_OS_MVP技术选型与工程工作流.md`

MVP 闭环：

```text
ROI 异常
  -> 指标口径确认
  -> 低效计划排行
  -> EvidenceChain
  -> 暂停/降预算/观察 ActionProposal
  -> R4/R5 风险审批
  -> 反馈 ROI、GMV、消耗、转化率
```

注意：

- 第一版不自动调整预算。
- 预算、价格、库存类动作必须只做提案和审批。
- ROI 低不等于一定暂停，必须结合消耗、GMV、转化漏斗和观察窗口。

典型问题：

- 今天 GMV 为什么下降？
- 哪个平台 GMV 环比下降最大？
- 转化漏斗哪个环节出了问题？
- 活动期 GMV 增幅是否达到预期？

推荐资料：

1. `05_业务问题与评测样本/黄金查询样本.md`
2. `05_业务问题与评测样本/业务问题样本.md`
3. `01_战略定位与技术PRD/AI_Native_Business_Data_OS_技术PRD与架构设计.md`

MVP 闭环：

```text
GMV 异常
  -> GMV / 订单 / CTR / 加购 / 支付 MetricContract
  -> 漏斗分解
  -> EvidenceChain
  -> 优先排查平台、品类、素材或库存
  -> 任务 / 审批
  -> 反馈异常处理结果
```

注意：

- 归因不要只靠模型文本，要绑定 SQL、时间窗口、对照组和限制说明。
- 结论要显示不确定性和待人工判断项。

## 9. 企业 Hybrid / 本地 Connector 试点

典型问题：

- 客户不允许数据库开放入站。
- 客户希望数据不出内网。
- 客户想使用自己的 AI Key、模型或 GPU。
- 客户已有本地 Agent、MCP Server、审批和工作流系统。

推荐资料：

1. `03_生态接入_安全算力_组织范式/AI_Native_Business_Data_OS_生态接入_安全算力与组织范式.md`
2. `04_知识资产_组织权限_部署架构/AI_Native_Business_Data_OS_知识资产_组织权限与部署架构.md`
3. `06_方案评估与落地边界/AI_Native_Business_Data_OS_MVP技术选型与工程工作流.md`

MVP 闭环：

```text
SaaS Control Plane
  -> Customer-side Connector Agent
  -> Outbound-only 通信
  -> 只读数据访问
  -> EvidenceChain
  -> ActionProposal
  -> 客户侧审批或任务系统
```

注意：

- 不要第一版承诺完整 Air-gapped。
- Local Connector 可以先是 Python service / CLI，不必先做 Electron。
- Electron 或 Tauri 应作为后续 Desktop Agent 外壳，而不是主产品形态。

5. `repo_scaffold/README.md`

MVP 闭环：

```text
需求
  -> 产品/项目经理 Agent 判断资料是否完备
  -> 架构师 Agent 输出方案
  -> CTO 审批
  -> 实现 Agent 编码
  -> Eval / Test / Review
  -> 文档和 ADR 更新
```

注意：

- Code Agent 的核心目标是提高工程吞吐，不是替代 CTO 或架构审查。
- 高风险改动必须走 ADR 和审批。
