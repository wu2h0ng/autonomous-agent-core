# AI Native Business Data OS 商业与技术竞争格局报告（内部版）

> 日期：2026-06-01  
> 用途：供创始团队、产品、技术、融资材料底稿使用。  
> 定位：回答市场上是否已有同行、我们应如何定位、短期如何收敛、长期如何拿下 AI-ready Data Foundation 到 Agent-ready Business Operation 的完整生态位。

---

## 1. 核心判断

市场上已经存在大量相邻玩家，但还没有一个完全同构的直接赢家。

我们所处的位置不是空白市场，而是一个正在快速成形的新交叉区：

```text
Agentic BI
  + Semantic Layer
  + Data Product / Evidence
  + Governed Business Action
  + Enterprise Knowledge Asset
```

短期看，最直接的竞争来自 Agentic BI 和 Data Agent 平台。其中 **Aloudata 是当前最核心的中国市场竞争者**，因为它同时覆盖 AIR 数据编织、BIG 主动元数据、CAN 指标平台和 Agent 分析智能体四条主线，已经占据了我们底座能力的核心参照系。帆软 Dora、SmartBI 白泽、ThoughtSpot Spotter、Tableau Next、Snowflake Intelligence 也是重要对手，但与本项目的重合度不如 Aloudata 全面。

长期看，真正的参照物是 Palantir AIP / Foundry。Palantir 已经证明，企业级 AI 的核心不是聊天框，而是把数据、语义、逻辑、行动、安全和反馈统一到业务对象与操作模型中。

我们的市场机会不在于绕开 Aloudata 做后半段“差异化”，而在于全面上位：他们能做的数据编织、元数据、指标平台、分析 Agent，我们要做得更自动、更广、更可执行；他们还没做深的行动、审批、反馈和知识资产，我们也要做。

因此，内部不能把本项目理解成“Aloudata 之上的 action layer”。更准确的生态位是：

```text
AI-ready Data Foundation
  + Agent-ready Business Operation
  + Enterprise Knowledge Asset
  = 企业 AI Agent 时代的业务生产操作系统
```

Aloudata 代表的 NoETL、Data Fabric、主动元数据、指标语义层和分析 Agent 是必须攻下的底座；本项目要继续向 Business Agent、OperationContract、Action Runtime、KnowledgeAsset、生态接入与治理能力延伸。

```text
可信问数
  -> EvidenceChain
  -> ActionProposal
  -> Approval
  -> OperationTrace
  -> Feedback
  -> KnowledgeAsset
```

如果我们只做自然语言问数，会进入帆软、SmartBI、Aloudata、ThoughtSpot、Tableau、Snowflake 的主战场。  
如果我们只做桌面文件和本地操作，会进入腾讯 Marvis、WPS、各类桌面 Agent 的主战场。  
如果我们只做行动治理，会变成 Aloudata 这类数据平台的上层插件。  
因此正确姿态是：**Aloudata 能做的事，我们要做得更好；Aloudata 不能做的事，我们也要做。**

## 2. 我们到底属于哪个市场

### 2.1 不应直接宣称的类别

| 类别 | 为什么不适合 |
|---|---|
| BI 工具 | 会被现有 BI 厂商按功能清单比较，落入图表、看板、取数、报表竞争 |
| ChatBI | 过窄，且准确率和语义层竞争已经拥挤 |
| Data Agent | 概念过泛，帆软 Dora、Aloudata Agent、SmartBI 白泽都已占位 |
| Agent 平台 | 过宽，会被 Dify、Coze、LangGraph、Agentforce、Copilot Studio 等拉入平台能力比较 |
| 桌面智能体 | 与 Marvis、WPS、本地文件助手竞争，偏个人生产力 |
| 数据中台 | 采购阻力大，容易被认为重建设、长周期、老范式 |

### 2.2 更准确的类别表达

建议内部使用：

```text
Business Data & Agentic Operations OS
```

建议对客户使用：

```text
可信业务数据行动平台
```

建议对投资人使用：

```text
Enterprise Agentic Business OS for AI-ready data, governed operations, and enterprise knowledge assets
```

中文可以表达为：

```text
企业 AI Agent 时代的业务生产操作系统
```

这句话不把产品降格为“替代 BI”或“通用 Agent 平台”，强调三件事：

1. 数据可信。
2. 行动受治理。
3. 反馈可沉淀。

## 3. 市场为什么现在发生

### 3.1 BI 正在从看板消费走向 Agentic Analytics

2024 到 2026 年，BI 和数据云厂商的共同方向非常明确：

- 自然语言问数。
- 语义层增强。
- 自动归因。
- 自动报告。
- 工作流推送。
- Agent 化分析助手。
- MCP / 第三方工具接入。
- 可治理模型和权限。

这说明一个事实：企业不再满足于“看报表”，而是希望数据系统主动理解问题、解释变化、生成下一步建议。

### 3.2 企业真正缺的是责任链

但大多数 Agentic BI 仍然停在：

```text
问数
  -> 分析
  -> 图表 / 报告
  -> 建议
```

企业真正痛的是后半段：

```text
建议是否有证据
谁批准
能不能追溯
能不能回滚
执行后效果如何
经验是否沉淀
下次是否更准
```

这就是我们要切入的地方。

### 3.3 AI 项目从 demo 进入治理期

企业对 AI Agent 的态度正在从“能不能做”转向“敢不敢用”。敢用的前提不是模型更强，而是：

- 数据口径稳定。
- 证据可追溯。
- 权限可控。
- 行动可审批。
- 成本可估算。
- 失败可复盘。
- 模型升级可回归。

因此，EvidenceChain 和 Evaluation Runtime 不是附属能力，而是商业化门槛。

## 4. 竞争格局分层

### 4.1 第一层：长期参照物，Palantir

Palantir AIP / Foundry 是最接近长期终局的产品体系。

公开文档显示，Palantir AIP 重点能力包括安全 LLM 集成、端到端 observability、context engineering、Ontology、tool services、安全治理、agent lifecycle、operational automation 等。它的 Ontology 将企业中的数据、逻辑、行动和安全整合为统一表示，并强调 actions、writeback、human review、audit 和 decision lineage。

对我们的启示：

1. 企业级 AI 的终局不是聊天，而是 operational domain。
2. 业务对象和行动必须进入语义层。
3. AI 要能做事，必须有 action guardrails。
4. 每个行动必须被记录、审计、反馈。
5. 长期护城河来自企业自己的 ontology、decision lineage 和 operational memory。

我们不能短期复刻 Palantir。它太重、太贵、太依赖交付。但我们可以抓住轻量切口：

```text
Palantir 做完整企业 ontology 和 operational AI
我们先做 EvidenceChain-first 的业务数据行动闭环
```

内部判断：Palantir 是北极星，不是 MVP 对手。

### 4.2 第二层：国内直接竞品，Aloudata、Dora、SmartBI 白泽

#### Aloudata AIR / BIG / CAN / Agent

Aloudata 是本项目当前最核心的国内竞争者，不只是“Agentic BI 相邻玩家”。它的产品家族覆盖：

- AIR：逻辑数据编织平台，强调跨源数据融合、逻辑建模、数据虚拟化、联邦查询和自适应物化加速。
- BIG：主动元数据平台，强调算子级血缘和 DataOps 治理。
- CAN：NoETL 自动化指标平台，强调指标定义、指标管理、指标开发、明细语义层和指标一致性。
- Agent：基于 NoETL 明细语义层的分析决策智能体，强调智能问数、归因解释、报告输出和趋势预测。

这意味着我们不能采取“他们做数据平台，我们做行动治理”的旁路打法。正确姿态是全面对标和上位替代：

| Aloudata 产品 | 他们能做的 | 我们要做得更好的 |
|---|---|---|
| AIR 数据编织 | 逻辑数据集成、数据虚拟化、联邦查询、查询加速 | ProviderContract 覆盖数据库、API、文件、浏览器采集、事件流、人工输入；DataProduct Compiler 从 BusinessIntent 自动生成数据获取和编译方案 |
| BIG 主动元数据 | 算子级血缘、技术元数据、DataOps 治理 | Semantic Object + DataProduct + EvidenceChain + OperationTrace，形成语义、数据、证据、行动四层元数据 |
| CAN 指标平台 | 指标定义、指标管理、口径一致、自动化生产 | MetricContract = 口径 + owner + quality contract + evidence template + action candidate + feedback metric |
| Agent 分析智能体 | NL2SQL、NL2MQL2SQL、对话分析、归因、报告、趋势预测 | Data Agent 完成同等分析，但输出 EvidenceChain；Business Agent 消费 EvidenceChain 生成 ActionProposal、Approval、OperationTrace、FeedbackAsset |

内部竞争口径：

```text
Aloudata 是数据工程的革新者。
我们是业务生产范式的重构者。

他们让数据更好。
我们让数据直接驱动业务。

他们优化数据怎么来、怎么管理、怎么分析。
我们重构业务意图到业务生产的完整责任链。
```

#### 帆软 Dora

Dora 被公开描述为“Data Agent 数字员工孵化平台”，结合 FineReport、FineBI、FineDataLink、知识库、LLM 和 Agentic Workflow，形成数据分析师、日报推送秘书、风险预警官、报告研究员等数字员工，完成即时问数、数据摘要、异常提醒、例行报告生成与定期推送。

优势：

- 帆软有强 BI 客户基础。
- 已有报表、BI、数据集成和权限体系。
- 在国内企业里有强服务网络和信任基础。
- “数字员工”包装比“Agent 平台”更容易被业务方理解。

限制：

- 路径大概率仍以 BI 和报表资产为中心。
- 行动闭环可能更多是报告、预警、推送和流程化任务。
- 是否具备完整 OperationContract、审批、回滚、反馈资产化，还需要继续观察。

对我们的竞争含义：

我们不能和 Dora 比“谁更懂 BI”。应该强调：

```text
Dora 激活 BI 资产
我们连接证据、行动、审批和反馈
```

#### SmartBI 白泽

SmartBI 白泽定位为企业级 AgentBI，强调智能问数、归因分析、智能报告，并宣称已有报表、仪表盘、数据集、指标模型都可以直接接入，存量 BI 资产可被 AI 激活。其公开页面也强调金融、政务、制造、能源、零售等行业落地。

优势：

- 大型企业 BI 交付经验。
- 存量 BI 资产激活叙事清晰。
- 准确率、指标模型、RAG、多智能体协同等工程话术成熟。
- 私有化和国产化接受度高。

限制：

- 核心仍然围绕“智能分析、归因、报告”。
- 行动建议更多停留在分析结果输出，未必进入受治理业务操作。
- 容易被既有 BI 产品边界限制。

对我们的竞争含义：

如果客户只想“问数更准、报告更快”，白泽是强对手。  
如果客户想“洞察之后怎么进入审批、任务、行动和复盘”，我们有切入口。

### 4.3 第三层：全球 Agentic BI，ThoughtSpot、Tableau、Qlik

#### ThoughtSpot Spotter

ThoughtSpot Spotter 和 Spotter Semantics 强调 agentic analytics、governed semantic foundation、policy-aware queries，并通过 MCP 和 Open Semantic Interchange 让受治理业务上下文进入外部 AI agent。

启示：

- 语义层正在从 BI 内部组件变成 Agent 时代的公共上下文协议。
- 决策语义会被外部 Agent 消费。
- 我们必须把 MetricContract 和 EvidenceChain 做成可被 Agent 和外部系统消费的对象，而不是页面内容。

风险：

- 如果 ThoughtSpot 进一步从 analytics agent 进入 action workflow，会侵入我们的后半段。

#### Tableau Next / Salesforce Agentforce

Tableau Next 被官方称为 agentic analytics platform，集成 Agentforce，强调 Tableau Semantics、Data 360、Action Layer、Marketplace、Salesforce 和第三方应用中的行动能力。

启示：

- Salesforce 正在把 analytics 和 enterprise action 结合。
- “数据洞察进入业务工作流”已经成为大厂方向。
- 如果客户已经深度使用 Salesforce，我们需要选择接入而不是替换。

风险：

- 在 CRM、销售、客服等领域，Salesforce 的系统入口极强。
- 第一阶段不把“Salesforce 内部数据 Agent”作为主战场，优先做跨系统和非 Salesforce 场景。

### 4.4 第四层：数据云控制面，Snowflake、Databricks、Microsoft Fabric

#### Snowflake Intelligence / Cortex

Snowflake 公开提出要成为 “control plane for the agentic enterprise”，Snowflake Intelligence 面向业务用户，把企业数据、工具、工作流与 AI agents 连接起来，并通过 MCP connector 接入 Gmail、Calendar、Docs、Jira、Salesforce、Slack 等工具。

启示：

- 数据云厂商不满足于做数据仓库，会向企业 AI 控制面扩张。
- MCP 和工具生态会成为标准动作。
- “turn insights into action” 已经是数据云叙事。

限制：

- 强依赖 Snowflake 数据云。
- 对非 Snowflake 客户或多云/混合环境，存在天然边界。

我们的机会：

```text
数据云厂商做云内控制面
我们做跨数据栈、跨 BI、跨业务系统的业务生产闭环 OS
```

#### Databricks AI/BI Genie

Databricks Genie 让业务团队用自然语言与数据交互，强调 governed self-service insight。它强在 Lakehouse、Unity Catalog、数据科学和工程一体化。

对我们的影响：

- Databricks 客户会倾向先用 Genie。
- 我们不应在 Lakehouse 内部问数体验上硬碰。
- 我们应围绕 EvidenceChain、行动提案、审批和反馈形成补充层。

#### Microsoft Fabric / Power BI Copilot

Microsoft 有 Power BI semantic model、Fabric、Teams、Office、Power Automate 等工作流入口。它的优势不是单点产品，而是生态协同。

对我们的影响：

- 微软客户有强替代路径。
- 但 Fabric Copilot 仍主要围绕语义模型、报表、DAX、分析和协同生产力。
- 我们可以选择成为跨系统证据链和行动治理层，而不是替代 Power BI。

### 4.5 第五层：桌面和本地 Agent，腾讯 Marvis

Marvis 官方页面强调本地大模型、本地模式文件 0 上传、手机操控电脑、文件智能整理搜索、一句话修改电脑设置、文档和表格深度理解。

Marvis 不是直接竞品，但它定义了两个重要用户预期：

1. 敏感数据可以本地处理。
2. Agent 执行过程应该可见、可接管。

对我们的启示：

- 后续必须有 Local Connector / Desktop Agent。
- 但桌面端不应成为主产品。
- 本地模式的卖点应服务企业数据边界，而不是个人文件整理。

我们的边界：

```text
Marvis: 个人电脑和本地文件的操作系统 Agent
我们: 企业 AI Agent 时代的业务生产操作系统
```

## 5. 竞争坐标系

可以用两个轴判断所有同行：

```text
横轴：从数据分析到业务行动
纵轴：从单点工具到企业治理运行时
```

| 象限 | 代表 | 特征 |
|---|---|---|
| 分析工具 | 传统 BI、ChatBI | 问数、图表、报告 |
| 治理分析平台 | FineBI、SmartBI、ThoughtSpot、Databricks Genie | 语义层、权限、指标、问答 |
| 行动助手 | Marvis、个人 Agent、RPA Agent | 可执行任务，但企业治理弱 |
| 业务数据操作层 | Palantir，未来可能的 Snowflake/Tableau | 数据、逻辑、行动、安全、反馈统一 |

我们的目标应落在第四象限，但 MVP 不能一口吃下整个象限。MVP 应从：

```text
治理分析平台
  -> EvidenceChain
  -> 行动提案
```

这一窄缝切入。

## 6. 我们的生态位吞并定义

### 6.1 不以问数为终点

同行常见链路：

```text
问题
  -> 指标/语义层
  -> SQL / 查询
  -> 图表 / 解释 / 报告
```

我们的链路：

```text
问题
  -> MetricContract
  -> DataProduct candidate
  -> SQL Safety
  -> EvidenceChain
  -> ActionProposal
  -> Approval
  -> OperationTrace
  -> Feedback
  -> KnowledgeAsset
```

### 6.2 EvidenceChain-first

多数产品强调准确率。我们应强调：

- 答案为什么可信。
- 指标口径来自哪里。
- SQL 是什么。
- 数据质量如何。
- 权限范围是什么。
- 结论限制是什么。
- 行动建议引用了哪些证据。

准确率是结果，EvidenceChain 是企业信任的机制。

### 6.3 Governed Action，而不是 Autonomous Action

我们不应宣传“AI 自动执行一切”。企业客户更需要：

- 风险分级。
- dry-run。
- 审批。
- 人类责任人。
- 可追溯。
- 可回滚或补偿。
- 执行反馈。

这比“全自动 Agent”更可信，也更容易进入企业采购。

### 6.4 兼容但不附庸

Dora、白泽、FineChatBI、Tableau、Power BI Copilot 都依附既有 BI 或数据平台。我们应该支持这些系统作为 Provider，但不能把自己定位成它们的补充插件。

对 Aloudata 尤其如此：AIR、BIG、CAN、Agent 都可以作为客户既有系统接入，但产品战略上必须形成上位替代能力，而不是默认把数据编织、元数据、指标平台和分析 Agent 让给它。

定位：

```text
兼容客户已有 BI、数仓、指标平台和数据编织系统
但核心能力必须覆盖从 BusinessIntent 到 DataProduct、EvidenceChain、ActionProposal、Feedback 的完整链路
在能接入对方能力的同时，具备逐步替代其关键能力的产品路径
```

### 6.5 轻量 Palantir

内部可以用 “Lightweight Palantir for business data action loops” 作为理解，但对外不要直接这么说。

更好的表达：

```text
用更轻的方式，让企业从可信数据证据走向受治理业务行动
```

## 7. 商业切入口

### 7.1 不卖 OS，先卖角色型闭环

第一阶段不要卖 “AI Native Business Data OS”。应卖：

| 包装 | 适用 |
|---|---|
| 可信经营分析师 | 经营分析、管理层周报、异常解释 |
| 异常诊断员 | ROI、GMV、库存、转化漏斗等异常归因 |
| 行动提案助手 | 把洞察转为任务、审批单、处理建议 |
| 复盘记录员 | 执行后沉淀反馈、案例、规则和评测样本 |

这些是客户能买的东西。

### 7.2 首发场景标准

首发场景必须满足：

1. 高频。
2. 指标明确。
3. 数据相对可得。
4. 行动建议可验证。
5. 风险可控。
6. 有业务 owner 每周评测。

内容电商、投放效率诊断、销售运营、客服运营、财务经营分析都可选。不要一开始做高风险自动执行。

### 7.3 客户价值表达

不要主打：

```text
少写 SQL
替代 BI
自动建数仓
全自动运营
```

应该主打：

```text
数据结论可信
异常诊断更快
行动建议可审批
复盘证据可追溯
高频分析流程可复用
业务和数据团队少扯皮
```

## 8. 技术竞争点

### 8.1 必须赢的技术点

| 技术点 | 为什么重要 |
|---|---|
| SemanticObject lite | 让业务实体、指标、规则和行动语义进入机器可读对象 |
| MetricContract | 没有稳定口径，Agent 问数不可生产 |
| ProviderContract lite | 数据访问必须通过能力、权限、成本、质量和血缘契约表达 |
| DataProduct candidate | 防止产品停留在问答层，让结果可复用、可回放 |
| SQL Safety | 企业信任底线 |
| EvidenceChain | 企业信任基础和正式答案准入门槛 |
| Eval Harness | 没有评测无法商业化 |
| ActionProposal | 从 BI 走向业务行动的桥 |
| Approval lite | 企业可控性的最小入口 |
| Trace lite | 审计和复盘基础 |

产品灵魂不是单一 EvidenceChain，而是 DataProduct Compiler、EvidenceChain、Governed Operation、Feedback 和 KnowledgeAsset 组成的业务生产闭环。

### 8.2 可以后置的技术点

| 技术点 | 后置原因 |
|---|---|
| 完整 Temporal | MVP 长流程还不稳定，先不要 workflow 化一切 |
| 完整 OPA | 策略早期变化大，先做 PolicyEngine 抽象和测试集 |
| 完整 OpenLineage | 先把 evidence 和 query trace 做扎实 |
| 完整 MCP Gateway | 第三方工具进入生产前再做重治理 |
| 完整 Domain Pack SDK | 第二个领域复用成功后再抽象 |
| 完整私有化 | 先做 SaaS / Hybrid 边界和 Connector Agent |
| 完整 Data Fabric / NoETL / Active Metadata | MVP 只做 AI-ready data foundation lite，避免被重型数据平台工程拖慢 |
| Trino / Calcite-style 联邦查询 | 等多源查询需求真实出现后再打开 |

### 8.3 技术护城河顺序

```text
第一层：golden query / golden business loop / eval pack
第二层：SemanticObject + MetricContract + ProviderContract
第三层：DataProduct Compiler + EvidenceChain schema
第四层：ActionProposal + OperationContract + approval / operation trace
第五层：FeedbackAsset + KnowledgeAsset
第六层：Domain Pack 和 Provider / Action Connector 生态
```

真正的护城河不是模型，也不是单个大数据组件，而是企业持续沉淀的语义契约、数据产品、业务证据、责任链、决策反馈和评测集。

## 9. 主要风险

### 9.1 被 Aloudata 上位压制

风险：如果我们只做行动治理，Aloudata 可以凭借 AIR、BIG、CAN、Agent 的底座优势向上补齐 ActionProposal 和审批，把我们压成上层插件。  
应对：我们必须拥有自己的 ProviderContract、DataProduct Compiler、Semantic Object、MetricContract、EvidenceChain 和 Business Agent Runtime。行动治理是终点，不是唯一壁垒。

### 9.2 被 AgentBI 厂商功能覆盖

风险：Dora、白泽、ThoughtSpot、Tableau 等很快补齐行动提案和审批模块。  
应对：我们必须把 EvidenceChain、OperationTrace、FeedbackAsset 和 KnowledgeAsset 做得比它们更产品化，而不是停在“建议”。

### 9.3 被数据云厂商平台化碾压

风险：Snowflake、Databricks、Microsoft 把数据云内的 Agent 能力做成标准。  
应对：强调跨数据栈、跨 BI、跨业务系统，不绑定单一数据云。

### 9.4 被 Palantir 叙事覆盖

风险：高端客户认为 Palantir 才是完整答案。  
应对：我们不争超大型企业全域 operational AI，先争中型企业和部门级闭环，成本和落地周期更轻。

### 9.5 MVP 过重

风险：试图同时做 Agent Runtime、MCP Gateway、OPA、Temporal、Domain Pack、私有化、完整 Data Fabric、完整 NoETL 和主动元数据平台。  
应对：P0 只做可信问数、AI-ready data foundation lite、EvidenceChain、ActionProposal、Approval lite、Eval。技术栈采用 FastAPI、Pydantic、PostgreSQL JSONB、pgvector、sqlglot、可选 DuckDB、自研 Agent Runtime 和自研 Eval Harness。

### 9.6 只做成报告生成器

风险：产品被客户理解为“智能报告工具”。  
应对：每个报告都必须有 ActionProposal 和 Feedback 入口。

## 10. 内部战略建议

### 10.1 产品策略

第一版只做：

```text
可信问数
EvidenceChain
行动提案
轻审批
反馈记录
评测回归
```

坚决不做：

```text
完整 OS
完整 Marketplace
全自动写操作
大而全数据集成
完整私有化
复杂桌面客户端
```

### 10.2 竞争策略

对 Aloudata：

```text
不是旁路差异化，而是全面对标和上位替代
AIR 能做的数据编织，我们用 ProviderContract + DataProduct Compiler 做得更自动、更广
BIG 能做的元数据，我们升级为语义、数据、证据、行动、反馈的生产元数据
CAN 能做的指标平台，我们升级为可执行 MetricContract
Agent 能做的分析，我们做同等能力并进入 Business Agent 行动闭环
```

对 BI 厂商：

```text
兼容 BI 资产，但不把自己限制为 BI 插件
必须覆盖从可信问数到行动反馈的完整链路
```

对数据云：

```text
我们不替代数仓，而是跨数据栈组织可信行动
```

对 Palantir：

```text
我们不卖重型 ontology 工程，而是先提供可落地的 EvidenceChain 闭环
```

对 Marvis：

```text
我们不做个人电脑助手，但会提供企业本地 Connector 和数据不出域能力
```

### 10.3 市场进入策略

先选一个业务域，做出 3 条黄金业务闭环：

```text
异常发现
  -> 证据链
  -> 行动提案
  -> 审批
  -> 执行反馈
  -> 复盘资产
```

只要这 3 条闭环成立，就可以继续产品化。否则不要扩模块。

## 11. 对外表达建议

### 11.1 一句话

```text
我们帮助企业把业务问题转化为可信数据证据，并把证据进一步转化为可审批、可追溯、可复盘的业务行动。
```

### 11.2 不是

```text
不是 BI 替代品
不是数仓替代品
不是通用聊天机器人
不是桌面自动化助手
不是让 AI 直接越权执行业务动作
```

### 11.3 是

```text
是企业 AI Agent 时代的业务生产操作系统：从可信数据生产，到受治理业务行动，再到知识资产沉淀。
```
