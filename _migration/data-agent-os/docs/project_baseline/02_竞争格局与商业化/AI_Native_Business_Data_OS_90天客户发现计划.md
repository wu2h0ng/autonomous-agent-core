# AI Native Business Data OS 90天客户发现计划

> 日期：2026-06-02  
> 用途：把战略判断转成客户发现执行计划，验证第一个付费业务闭环从哪里来。  
> 原则：先验证客户、预算、场景和转化路径，再扩大产品范围。  
> 结论：未来 90 天的核心任务不是继续定义 Agent OS，而是找到 2-3 个愿意共创的旅伴客户，并锁定第一个可付费业务闭环。

---

## 1. 90天目标

90 天结束时，必须回答 6 个问题：

```text
1. 第一个真实 ICP 到底是谁？
2. 他们最痛的业务问题是什么？
3. 现有系统为什么解决不好？
4. 谁有预算，谁会反对？
5. POC 如何转成付费合同？
6. MVP 应该只做哪一个业务闭环？
```

90 天的可验收结果：

| 目标 | 验收标准 |
|---|---|
| 客户发现 | 完成 30 个目标客户触达、12 个深度访谈、5 个二次访谈 |
| 旅伴客户 | 筛出 2-3 个愿意每周共创、提供真实数据样本和业务问题的客户 |
| 首发场景 | 锁定 1 个行业、2-3 个高价值业务问题、1 条可演示业务闭环 |
| 付费假设 | 明确 POC 转付费条件、预算 owner、采购阻力和可能 ACV 区间 |
| MVP 边界 | 输出首个业务闭环的 MetricContract、EvidenceChain、ActionProposal 和验收指标 |

如果 90 天后无法找到至少 2 个强意愿旅伴客户，应暂停扩大工程投入，重新审视 ICP 和切入场景。

## 2. 核心假设

本计划验证的是以下生存级假设：

| 假设 | 为什么重要 | 验证方式 |
|---|---|---|
| H1：目标客户存在高频、高价值、当前解决不好的业务数据问题 | 没有强痛点就没有采购理由 | 深访中确认问题频率、影响金额、现有替代方案 |
| H2：客户不愿迁移系统，但愿意让新控制面编排现有系统 | 决定产品是替换型还是兼容编排型 | 询问是否接受接入数仓、BI、业务系统、审批系统 |
| H3：EvidenceChain 是准入门槛，不是付费理由 | 避免把可信误当核心卖点 | 观察客户是否因业务结果而非可信概念表达购买意愿 |
| H4：ActionProposal 比普通问数更接近预算 | 决定是否从问数走向业务行动 | 验证客户是否愿意让系统生成建议、任务或审批流 |
| H5：客户愿意在 POC 期沉淀 MetricContract 和业务规则 | 决定知识资产护城河能否开始形成 | 要求客户共同维护指标口径、golden query、复盘记录 |
| H6：数据团队可以被转化为配置者和治理者 | 避免内部反对导致采用失败 | 访谈数据团队，确认其是否接受 MetricContract Owner 角色 |

## 3. 第一版 ICP

### 3.1 优先客户

| 维度 | 标准 |
|---|---|
| 行业 | 内容电商、新消费品牌、DTC、零售连锁、SaaS 增长团队 |
| 企业规模 | 100-2000 人，年营收 3000 万-50 亿 |
| 数据基础 | 已有数据库、数仓、BI、报表或数据团队，仍存在口径和响应问题 |
| 业务痛点 | GMV、ROI、库存、转化、销售、客服、现金流中至少一个问题高频发生 |
| 组织条件 | 有业务 owner、数据 owner、预算 owner；愿意每周共创 |
| 技术态度 | 不排斥 AI，但不接受黑盒自动执行 |

### 3.2 暂不优先客户

| 类型 | 原因 |
|---|---|
| 没有基础数据系统的小微企业 | 需要先帮它建数据基础设施，偏项目制 |
| 强监管金融、医疗、政务 | 合规和采购周期过重，不适合第一阶段 |
| 超大型集团总部 | 销售周期过长，容易陷入长期 POC |
| 只想买 ChatBI 的客户 | 容易落入功能对比和低价竞争 |
| 只关注模型能力的客户 | 不会为业务闭环和知识资产付费 |

## 4. 旅伴客户评分卡

每个候选客户按 100 分打分。低于 70 分不进入深度共创。

| 维度 | 分值 | 评分标准 |
|---|---:|---|
| 痛点强度 | 20 | 问题是否每周发生，是否影响收入、成本、周转或风险 |
| 数据可用性 | 15 | 是否能提供真实数据样本、Schema、指标口径和历史报表 |
| 业务 owner 意愿 | 15 | 是否有业务负责人愿意每周参与评审 |
| 数据 owner 配合 | 15 | 数据团队是否愿意提供口径、SQL、权限和验证 |
| 预算可能性 | 15 | 是否存在明确预算来源和采购 owner |
| 付费时间窗口 | 10 | 3-6 个月内是否可能从 POC 转合同 |
| 案例价值 | 10 | 是否能形成可复用 Domain Pack 或公开/半公开案例 |

强旅伴客户标准：

```text
总分 >= 80
痛点强度 >= 15
业务 owner 意愿 >= 12
数据可用性 >= 10
```

如果客户分数高但不愿意提供真实数据样本，只能作为访谈对象，不能作为旅伴客户。

## 5. 访谈对象与问题

### 5.1 业务负责人

目标：验证是否有高价值业务问题和预算动机。

必问问题：

1. 过去 30 天里，哪个业务问题最依赖数据判断？
2. 这个问题当前从提出到拿到可信结论需要多久？
3. 如果判断慢或判断错，影响是什么？
4. 你现在如何决定下一步行动？谁审批？
5. 你愿意让系统生成行动建议吗？哪些动作绝不能自动化？
6. 如果系统每周稳定帮你解决这个问题，你愿意从哪个预算支付？
7. 你需要看到什么结果，才会从 POC 转付费？

强信号：

- 客户能说出具体损失或机会成本。
- 客户主动提到“这个问题每周都发生”。
- 客户愿意让团队提供真实数据样本。
- 客户能指出预算来源。

弱信号：

- 只说“挺有意思”“可以试试”。
- 不能说清现有流程和损失。
- 没有业务 owner，只让 IT 或数据团队对接。

### 5.2 数据负责人 / 数据团队

目标：验证数据可用性、口径复杂度和内部阻力。

必问问题：

1. 业务最常问的 20 个指标是什么？
2. 哪些指标口径争议最大？
3. 现在用什么工具交付数据需求？BI、SQL、Excel 还是飞书/钉钉报表？
4. 一个新报表或分析需求平均要多久？
5. Schema、口径、权限变更现在如何管理？
6. 如果引入 MetricContract Owner / Eval Curator 角色，团队是否接受？
7. 你最担心 AI 系统犯什么错误？

必须收集的材料：

- 3-5 个真实业务问题。
- 3-5 条现有 SQL 或报表截图。
- 核心指标口径说明。
- 可脱敏的数据 Schema。
- 数据权限和审批边界。

### 5.3 IT / 安全 / 架构负责人

目标：验证部署、合规和集成阻力。

必问问题：

1. 数据是否允许出域？
2. 是否接受 SaaS、Hybrid、Customer VPC 或私有化？
3. 当前身份系统、审批系统、日志审计系统是什么？
4. 是否允许接入 OpenAI-compatible API、国产模型或 BYO Key？
5. 对第三方工具调用、MCP、Webhook、RPA 的限制是什么？
6. POC 阶段最小安全审批流程是什么？

## 6. 首发场景筛选标准

首发场景必须同时满足：

| 标准 | 要求 |
|---|---|
| 高频 | 至少每周发生 |
| 高价值 | 能影响收入、成本、库存、转化、现金流或风险 |
| 数据可得 | 所需数据可以在 2 周内接入或导出 |
| 低到中风险 | 第一阶段不涉及不可回滚的高风险写操作 |
| 可验证 | 行动后 24 小时到 14 天内能观察反馈指标 |
| 可复用 | 能沉淀为行业 Domain Pack，而不是一次性项目 |

优先场景候选：

| 场景 | 为什么优先 |
|---|---|
| 投放 ROI 异常归因与调整建议 | 高价值、高频、反馈快，适合 EvidenceChain + ActionProposal |
| GMV 下滑归因与行动提案 | 管理层关注，容易形成业务闭环 |
| 库存风险与补货建议 | 结果可验证，适合审批和任务流 |
| 销售 pipeline 异常与跟进行动 | SaaS 和 B2B 客户可复用 |
| 客服问题聚类与知识更新 | 低风险，容易形成 KnowledgeAsset |

第一阶段不选：

- 财务付款、合同签署、价格大幅调整、权限变更、删除数据等高风险动作。
- 纯问数、纯报表、纯聊天入口。
- 需要大规模数据治理后才能启动的项目。

## 7. 90天执行节奏

### Week 1-2：准备与名单

交付物：

- ICP 一页纸。
- 50 个目标客户名单。
- 3 套访谈脚本：业务负责人、数据负责人、IT/安全负责人。
- 旅伴客户评分表。
- POC 转付费假设表。

验收：

```text
至少完成 10 个有效触达。
至少约定 5 个深度访谈。
```

### Week 3-4：第一轮深访

交付物：

- 8-10 份访谈纪要。
- 高频业务问题列表。
- 客户现有系统和数据基础设施地图。
- 第一版首发场景排序。

验收：

```text
至少识别 3 个强痛点客户。
至少拿到 2 个客户的脱敏数据结构或真实报表样本。
```

### Week 5-6：二次访谈与场景收敛

交付物：

- 5 个候选客户评分卡。
- 2-3 个旅伴客户候选。
- 每个候选客户的业务闭环草图。
- 20 条候选 golden question / golden query。

验收：

```text
至少 2 个客户愿意每周参与共创。
至少 1 个客户愿意提供真实指标口径和现有 SQL / 报表。
```

### Week 7-8：闭环原型定义

交付物：

- 首个业务闭环 PRD lite。
- MetricContract 初版。
- EvidenceChain 字段模板。
- ActionProposal 模板。
- 审批和反馈路径设计。

验收：

```text
一个具体业务问题可以被拆成：
BusinessIntent -> DataRequirement -> MetricContract -> EvidenceChain -> ActionProposal -> FeedbackMetric
```

### Week 9-10：POC 方案与商业假设

交付物：

- POC 方案模板。
- 参照客户协议要点。
- 付费转化条件。
- 预算 owner / veto owner 地图。
- ACV 区间假设。

验收：

```text
至少 1 个客户确认 POC 成功后存在付费可能。
至少 1 个客户愿意进入 POC 排期。
```

### Week 11-12：决策复盘

交付物：

- 90 天客户发现复盘。
- MVP scope 决策。
- 首个业务闭环验收指标。
- 是否继续投入工程资源的决策建议。

验收：

```text
Go：2-3 个旅伴客户 + 1 个明确业务闭环 + 1 个 POC 排期。
No-Go：客户只愿意免费试用、没有真实数据、没有预算 owner。
Pivot：痛点存在，但行业、客户规模或切入场景需要调整。
```

## 8. POC设计原则

POC 不能做成免费咨询或免费定制项目。

必须满足：

1. 有明确开始和结束日期，建议 4-6 周。
2. 有客户侧业务 owner、数据 owner 和决策 owner。
3. 使用真实但可脱敏的数据。
4. 只验证 1 条业务闭环，不扩散成通用平台试用。
5. POC 开始前定义转付费条件。
6. POC 过程中沉淀客户专属 MetricContract、EvidenceChain 和 golden query。
7. POC 结束时必须做 ROI / 业务价值复盘。

POC 成功指标示例：

| 指标 | 目标 |
|---|---|
| golden query 正确率 | 核心问题 >= 90%，进入生产前 >= 95% |
| EvidenceChain 生成时间 | P95 < 10 秒，MVP 可接受 < 30 秒 |
| 用户主动使用 | 每周 >= 3 次 |
| ActionProposal 采纳 | 至少 1 条被真实业务采纳或进入审批 |
| 决策周期缩短 | 从天级降到小时级，或明确减少人工分析步骤 |
| 客户资产沉淀 | >= 10 条 MetricContract，>= 10 条 EvidenceChain 历史 |

---

## 9. 反模式

以下情况必须主动停止：

| 反模式 | 为什么危险 |
|---|---|
| 客户只愿意“看看 demo” | 不能验证真实痛点和付费意愿 |
| 客户不给真实数据样本 | 无法验证 EvidenceChain 和 MetricContract |
| 客户只有 IT 对接，没有业务 owner | 业务闭环无法落地 |
| POC 目标不断扩张 | 会变成免费项目制交付 |
| 客户要求先做完整连接器 | 会把团队拖进 connector 地狱 |
| 讨论长期平台生态多于讨论一个具体业务问题 | 战略正确但验证失败 |

## 11. 90天最终决策标准

### Go

继续推进 MVP 工程和 POC。

条件：

- 至少 2 个强旅伴客户。
- 至少 1 个明确 POC 排期。
- 至少 1 条业务闭环可用真实数据验证。
- 客户明确表达 POC 转付费条件。

### No-Go

暂停工程投入，重新审视方向。

触发条件：

- 客户只愿意免费试用，不愿投入真实业务资源。
- 找不到预算 owner。
- 业务痛点弱，客户把产品理解成普通 ChatBI。
- 数据不可得或接入成本远高于业务价值。

### Pivot

调整 ICP 或场景，不推翻长期愿景。

触发条件：

- 痛点真实，但首发行业不对。
- 业务 owner 愿意，但数据团队阻力过大。
- 问数需求强，但行动闭环短期无法进入。
- 客户更愿意为兼容接入 / 数据口径治理付费，而不是 ActionProposal。
