# AR-20260614: P5.1b — adoption-driven knowledge promotion (close the self-report fold)

- Status: Accepted (founder-directed P5.1b execution, 2026-06-14)
- Parent: `docs/decisions/ADR-0001-p5-substrate-harvest.md` (P5.1b row + §4b last line)
- Touches (requires AR per CLAUDE.md): Feedback / KnowledgeAsset behavior. OS Core only; no contract/schema change.

## 1. Context — the leak P5.1a left open

P5.1a split realized external value into an operator-exclusive adoption ledger and gave the runtime a read-only view. But `TrustedLoopRuntime.record_outcome` still **folded the runtime's own SELF-REPORT feedback into knowledge** (`with_feedback` + `register_version`, version bump). So the runtime could still grow/revise its own knowledge by self-reporting `"adopted"` — the wirehead path the channel split was meant to close. This AR completes the closure (the "stake = non-bypassable mediation" harvest, P5 memo M3).

## 2. Decision

**Value-driven knowledge promotion is driven by the adoption ledger (realized external value), never by self-report.**

- `record_outcome` (self-report): records the typed `FeedbackEvent` to the feedback store as an **observation only**. It no longer touches knowledge. (Source stays `RUNTIME_SELF_REPORT`, P5.1a.)
- New `promote_from_adoption(trace_id)`: reads the adoption ledger via the **read-only** `AdoptionLedgerView`; if realized-value events exist and a knowledge candidate exists for the trace, supersedes it with a revision reflecting the latest adoption outcome (`with_feedback` + `register_version`), atomically under the configured unit of work. Returns the revised asset, or `None` (no view wired / no adoption / no base asset).

The runtime still holds NO adoption writer (P5.1a invariant preserved): only an operator-held `AdoptionIngest` attests realized value; the runtime can only read it and fold it into knowledge.

## 3. Engineering-flow specification

- **Real entry point**: the composition layer holds the factory-built runtime and the operator's `factory.adoption_ingest()`. After the operator attests adoption (`ingest.submit(trace_id, outcome)`), it calls `runtime.promote_from_adoption(trace_id)` over the SAME ledger. Exercised end-to-end by `test_factory_postgres_store.py`. (A dedicated CLI/HTTP operator `adopt` surface is the natural next wiring — documented pending; the capability + composition entry point + regression are in place now.)
- **Contract/schema**: unchanged. Reuses `FeedbackEvent` (source `EXTERNAL_ADOPTION`) and `KnowledgeAsset`.
- **Happy path**: operator attests adoption → `promote_from_adoption` bumps the trace's knowledge version, revision carries `outcome`.
- **Negative/refusal paths**: self-report `record_outcome` does NOT change knowledge version (regression below); `promote_from_adoption` with no view / no adoption / no base asset is a no-op returning `None`.
- **Regression that fails if bypassed**: `test_self_report_does_not_promote_knowledge` fails if `record_outcome` ever re-introduces a knowledge fold (the wirehead); `test_adoption_promotes_knowledge` fails if adoption stops driving promotion.
- **Trace/evidence/feedback/knowledge update**: self-report → feedback store (audit); realized adoption → knowledge version bump. Self-report and external value remain schema-separated and never co-aggregated (P5.1a).
- **OS Core boundary**: change is entirely within `agent_os_core`; no import of domain/persistence/connectors; the runtime reads adoption through the injected read-only view.

## 4. Acceptance

```text
P5.1b-i  self-report record_outcome leaves knowledge version unchanged (wirehead closed);
         promote_from_adoption is the ONLY path that promotes knowledge, and only from realized
         external value read through the read-only view.
```
